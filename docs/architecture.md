# Архитектура и стек

## Стек

| Слой | Технологии |
|---|---|
| Frontend | Vue 3, TypeScript (strict), Vite, vue-router, Pinia, PrimeVue 4.5 (MIT), primeicons 7 |
| Backend | Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 (sync, psycopg 3), Alembic, PyJWT, Pillow (обработка фото) |
| База данных | PostgreSQL 16 |
| Тесты | pytest (backend), Vitest (frontend) |
| Запуск | Docker Compose |

## Схема

```text
 браузер
    |
    v
 +--------------+   HTTP/JSON   +--------------+   SQL   +--------------+
 | web          | ------------> | api          | ------> | db           |
 | Vue 3 + Vite |    /api/*     | FastAPI      |         | PostgreSQL   |
 +--------------+               +--------------+         +--------------+
        \__________________ docker compose __________________/
```

- `web` — SPA. Обращается к backend по префиксу `/api`. В разработке dev-сервер Vite (порт 5173) проксирует `/api` на `VITE_API_PROXY_TARGET` (`http://api:8000` в compose), поэтому браузер видит один origin и CORS не нужен.
- `api` — REST API. Вся бизнес-логика и проверки (включая лимиты) выполняются здесь, не на клиенте.
- `db` — единственное хранилище состояния, включая файлы фото мероприятий. Схема меняется только миграциями Alembic.

## Backend: ключевые решения

- Слои: `routers` → `services` → `models`. Роутеры не работают с БД напрямую.
- Время берётся из `app.state.clock`, а не из `datetime.now()`, чтобы тесты управляли временем.
- Операции, чувствительные к гонкам, сериализуются средствами PostgreSQL: advisory-лок по номеру телефона, атомарный `UPDATE ... RETURNING`, уникальные индексы.
- Тесты работают на реальном PostgreSQL (БД `app_test`): миграции применяются один раз за сессию, таблицы очищаются между тестами.
- Фото мероприятий хранятся в PostgreSQL в двух таблицах: `event_photos` (порядок, тип, размер; `position` 0–9, отложенный `UNIQUE (event_id, position)`) и `event_photo_data` (`bytea`). Запросы мероприятий читают только `id` фото (`photos` в ответе), байты отдаёт одна ручка `GET /events/{id}/photos/{photo_id}` с `Cache-Control: private, max-age=31536000, immutable` — фото с данным `id` не меняется. Каскад удаляет фото вместе с мероприятием. У каждого фото есть уменьшенная копия (`event_photo_data.thumb`, WebP шириной до 800 px), её отдаёт та же ручка с `?size=thumb` — каталог и миниатюры не скачивают исходники.
- Категории: у каждой есть `icon` (имя primeicons, `CHECK` по шаблону `^pi-[a-z0-9-]+$`) и обязательная картинка — `categories.cover_id NOT NULL` ссылается на `category_covers` (полная картинка и копия, `ON DELETE RESTRICT`). Картинку отдаёт `GET /categories/{id}/covers/{cover_id}`; новая картинка — новый `cover_id` и новый адрес, поэтому кеш бессрочный. Чтобы добавить категорию, миграция вставляет её вместе с картинкой и иконкой; картинка по умолчанию генерируется `api/scripts/generate_category_covers.py` (см. `api/migrations/assets/category_covers/README.md`).
- Поиск в каталоге — параметр `q` у `GET /events`: подстрока в названии через `ILIKE` без учёта регистра, `\`, `%` и `_` экранируются; применяется вместе с остальными фильтрами.
- Набор фото меняется целиком: `PUT /events/{id}/photos` (multipart: `order` — JSON-порядок из `{"id"}` и `{"file": n}`, части `files`). Права проверяются до чтения файлов, файлы проверяются и пересохраняются Pillow (`app/services/photo_processing.py`: тип по содержимому, поворот по EXIF, без метаданных) до блокировки строки мероприятия, замена — под `FOR UPDATE` в одной транзакции.

## Frontend: ключевые решения

- Сессия: access-токен только в памяти, refresh-токен в `localStorage` (`ik.refreshToken`). При загрузке страницы сессия восстанавливается через `POST /auth/refresh`.
- При 401 клиент один раз обновляет токены и повторяет запрос. Обновление single-flight: одновременные запросы ждут один и тот же промис, потому что backend ротирует refresh-токен.
- Гард маршрутов: гость → `/login`, незаполненный профиль → `/onboarding`, заполненный → главная `/` (список мероприятий). Страницы грузятся лениво.
- Вкладка, период, поиск и фильтры списка мероприятий хранятся в адресе (`/?tab=joined&period=past&category=3&q=йога`): ссылки и «Назад» восстанавливают список. Ответы на устаревшие запросы списка игнорируются.
- Мероприятие открывается окном поверх списка: `/events/:id` — дочерний маршрут `/`, поэтому `EventsView` остаётся смонтированным и сохраняет вкладку, фильтры и подгруженные страницы. Карточки ссылаются на окно с текущим query списка; список следит за параметрами по их содержимому и не перезагружается при открытии окна. Окно обновляет карточку под собой через `provide`/`inject` (`replaceItem`, `removeItem`).
- Контакты: Telegram организатора сервер отдаёт только записанным участникам и администратору, Telegram участников — в списке участников (он доступен только им же). Фото — по `photo_url` из профиля, при ошибке загрузки — инициалы.
- Фото мероприятий загружаются `fetch` с access-токеном (`apiFetchBlob`) и показываются по `blob:`-ссылке: `<img src>` не может передать заголовок `Authorization`. Кеш `usePhotoUrl` хранит ссылки по ключу (`id` фото и размер, `cover_id` картинки категории) до выхода из аккаунта (`clearPhotoCache` в `session.clear()`).
- Карточка каталога (`EventListCard`) показывает обложку `EventCover`: копия основного фото → копия картинки категории → фон с иконкой. Поиск в панели фильтров отправляется через 300 мс после ввода; быстрые фильтры («Есть свободные места», «На этой неделе») не хранят своего состояния — подсветка вычисляется из фильтров в адресе.
- Фото в форме мероприятия (`EventPhotosField`) — черновики в `useEventForm`; по «Создать»/«Сохранить» сначала уходят поля (`POST`/`PATCH`), затем, если набор изменился, `PUT` фото. Если фото не сохранились, форма остаётся открытой, а повтор не отправляет поля ещё раз.
- Окно создания мероприятия одно на приложение (`CreateEventDialog` в `App.vue`), открывается через `useCreateEventDialog()` из шапки и с пустой вкладки «Организую».
- Поля мероприятия (`EventFieldInput`) общие для окна создания и редактирования на месте; логика формы — `useEventForm`, по образцу `useProfileForm`.
- Права в интерфейсе (кнопки управления, запись) — подсказки по данным мероприятия и профиля; проверяет их backend, после каждого действия страница перезапрашивает данные.
- Подсказка с тестовым кодом (`DevCodeHint`) — временный костыль до SMS. Она показывается, только если `GET /api/auth/test/code` ответил 200. Удаляется вместе с `getTestCode`.
- Адаптивность mobile-first, правила — в [rules.md](rules.md#ui).
