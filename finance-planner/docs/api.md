# API-контракт финансового планера

Документ фиксирует соглашения API, форматы ошибок, полный список маршрутов и поля каждого ресурса. Устройство сервиса и модель данных описаны в [architecture.md](architecture.md). На 27 ноября 2026 г. реализованы `GET /api/health`, шесть маршрутов пользователя и входа, а также 14 маршрутов счетов, категорий и операций. Остальные появляются по шагам: номер шага стоит в таблице раздела 3, а сами шаги перечислены в [architecture.md](architecture.md), раздел 8.

## 1. Соглашения

1. Все маршруты начинаются с `/api`. Тела запросов и ответов передаются в JSON в кодировке UTF-8. Кириллица в ответах приходит экранированной: слово «Счёт» выглядит как `\u0421\u0447\u0451\u0442`. В примерах ниже она показана как есть.
2. Вход выполняется по сессионной куке `sessionid`. Без сессии доступны проверка сервиса, выдача токена CSRF, регистрация и вход, а в окружении разработки ещё страница `/api/docs` и описание `/api/openapi.json`.
3. Каждый запрос POST, PATCH и DELETE несёт заголовок `X-CSRFToken` со значением куки `csrftoken`. Куку выдаёт `GET /api/auth/csrf`. После входа Django меняет токен, поэтому клиент читает куку перед каждым изменяющим запросом.
4. Денежные суммы передаются строками. В запросе это строка из цифр с необязательной дробной частью: до 12 цифр, точка и одна или две цифры после неё, например `"1250.5"`. Пробелы, знак плюс, запятая и экспонента не допускаются, минус разрешён только там, где это сказано в описании поля. Число JSON вместо строки отклоняется с кодом 422. В ответе сумма всегда содержит два знака после точки: `"1250.50"`.
5. Даты записываются строкой `ГГГГ-ММ-ДД`, месяц строкой `ГГГГ-ММ`. Моменты времени идут в формате ISO 8601 в UTC с буквой `Z`, например `2026-11-18T08:50:45.527Z`. Доли секунды указываются до миллисекунд и опускаются, если равны нулю. Дата в query-параметре проверяется по тому же шаблону, что и в теле.
6. Идентификаторы и другие целые значения в теле запроса передаются числами JSON, логические значениями `true` и `false`. Строка `"3"` вместо числа даёт 422. Имена полей и параметров пишутся в `snake_case`.
7. У текстовых полей, кроме пароля, пробелы по краям обрезаются. Регистр букв в названиях и в логине учитывается.
8. Список возвращается объектом с массивом `items`. У постраничного списка рядом стоит `count`, общее число записей. Страницу задают параметры `page` (с единицы) и `page_size` (по умолчанию 50, значение больше 100 заменяется на 100). Страница за концом списка отдаёт пустой `items`.
9. Фильтры и сортировка передаются query-параметрами. Неизвестные query-параметры игнорируются. Идентификатор чужого объекта в фильтре даёт пустой список. Начало периода позже конца даёт 422.
10. Запрос PATCH меняет только присланные поля. Пустой объект допустим и ничего не меняет.
11. Лишнее поле в теле запроса отклоняется с кодом 422. Так же отклоняется в PATCH поле, которое задаётся только при создании. У выхода тела нет, и присланное тело сервер не читает.
12. Создание отвечает кодом 201 и созданным объектом. Запросы, на которые нечего вернуть (удаление, выход, выдача токена), отвечают кодом 204 без тела. Остальные успешные запросы отвечают кодом 200.
13. Чужой или несуществующий объект в пути запроса даёт 404. Идентификатор чужого или несуществующего счёта либо категории в теле запроса даёт 422 с указанием поля, текст в обоих случаях один.
14. Дата операции и перевода не может быть позже сегодняшнего дня пользователя. «Сегодня» считается по часовому поясу из его профиля.
15. Поля с пометкой «с шага N» появляются в ответах вместе с этим шагом.

## 2. Ошибки

Ошибка API приходит объектом JSON с двумя полями: `code` несёт машинный код, `detail` несёт текст по-русски, а у ошибок ввода массив. Интерфейс выбирает действие по полю `code` и не разбирает текст.

| HTTP | `code` | Когда возникает | Что делает интерфейс |
| --- | --- | --- | --- |
| 400 | `bad_request` | Тело запроса не разбирается как JSON: оно испорчено, больше 2.5 МБ или пришло формой, в том числе испорченной | Показывает общий сбой |
| 401 | `not_authenticated` | Нет сессии | Переводит на `/login` |
| 401 | `invalid_credentials` | Неверная пара логина и пароля при входе | Показывает текст в форме входа |
| 403 | `csrf_failed` | Нет токена CSRF или он устарел | Получает токен заново и повторяет запрос один раз |
| 403 | `common_category` | Попытка изменить или удалить общую категорию | Показывает уведомление |
| 404 | `not_found` | Объект из пути не найден среди объектов пользователя | Показывает уведомление и обновляет список |
| 409 | `account_in_use`, `category_in_use` | Удаляется счёт или категория, на которые есть ссылки | Показывает уведомление с текстом из `detail` |
| 409 | `transfer_operation` | Меняется или удаляется операция, которая входит в перевод | Показывает уведомление |
| 409 | `account_archived` | Включается правило, счёт которого в архиве | Показывает уведомление |
| 422 | `validation_error` | Ошибка ввода или нарушение правила планера | Показывает тексты под полями формы |
| 429 | `too_many_requests` | Слишком много попыток входа. Появится на шаге 24, если будет добавлено ограничение | Показывает уведомление, повтор после срока из заголовка `Retry-After` |
| 500 | `internal_error` | Неожиданный сбой на сервере | Показывает общий сбой с кнопкой повтора |

Три ответа приходят не в этой форме, интерфейс показывает их как общий сбой.

1. Код 405 на метод, которого у пути нет: текст `Method not allowed` и заголовок `Allow` со списком методов.
2. Страница 404 в HTML на путь, которого нет среди маршрутов.
3. Ошибка прокси, когда сервис `api` недоступен.

Код 503 отдаёт только `GET /api/health`: тело у него обычное, со статусом `degraded`.

Обработчики ошибок Django Ninja в корневом роутере заменены своими, они лежат в `api/finance_planner/errors.py`. Тесты проверяют форму ответов 400, 401 обоих видов, 403 `csrf_failed`, 404, 422, 429 и 500. Ответы 409 и 403 `common_category` проверяют тесты маршрутов счетов, категорий и операций.

**400.**

```json
{"code": "bad_request", "detail": "Тело запроса не разбирается как JSON"}
```

**401.** Первый ответ приходит на любой защищённый маршрут без сессии, второй на неудачный вход. Что именно неверно, логин или пароль, сервер не уточняет.

```json
{"code": "not_authenticated", "detail": "Требуется вход"}
```

```json
{"code": "invalid_credentials", "detail": "Неверный логин или пароль"}
```

**403.** Первый ответ приходит на изменяющий запрос без токена CSRF, второй на попытку изменить общую категорию.

```json
{"code": "csrf_failed", "detail": "Нет токена CSRF или он устарел"}
```

```json
{"code": "common_category", "detail": "Общую категорию нельзя изменить или удалить"}
```

**404.**

```json
{"code": "not_found", "detail": "Объект не найден"}
```

**409.**

```json
{"code": "account_in_use", "detail": "Счёт нельзя удалить: на него ссылаются операции. Его можно перенести в архив"}
```

**422.** Поле `detail` несёт массив, каждый элемент описывает одну ошибку. Поле `loc` показывает место: у тела запроса это `["body", "payload", "<поле>"]`, у query-параметра `["query", "<параметр>"]`, у параметра пути `["path", "<параметр>"]`. Поле `type` несёт вид ошибки, `msg` текст, `ctx` дополнительные сведения, если они есть.

```json
{
    "code": "validation_error",
    "detail": [
        {"type": "greater_than", "loc": ["body", "payload", "amount"], "msg": "Input should be greater than 0", "ctx": {"gt": "0"}},
        {"type": "missing", "loc": ["body", "payload", "date"], "msg": "Field required"},
        {"type": "extra_forbidden", "loc": ["body", "payload", "user_id"], "msg": "Extra inputs are not permitted"}
    ]
}
```

Ошибки, которые формулирует сам планер, приходят в той же форме с видом `planner_format` или `planner_rule` и русским текстом:

```json
{
    "code": "validation_error",
    "detail": [
        {"type": "planner_format", "loc": ["body", "payload", "amount"], "msg": "Сумма записывается строкой вида 1250.50"},
        {"type": "planner_rule", "loc": ["body", "payload", "account_id"], "msg": "Счёт в архиве"}
    ]
}
```

**429.** Заголовок `Retry-After` несёт число секунд до следующей попытки.

```json
{"code": "too_many_requests", "detail": "Слишком много запросов. Повторите позже"}
```

**500.** Трассировка пишется в журнал контейнера, в ответ она не попадает.

```json
{"code": "internal_error", "detail": "Внутренняя ошибка сервера"}
```

**503.** Отвечает только `GET /api/health`, когда база недоступна.

```json
{"status": "degraded", "python_version": "3.14.9", "django_version": "6.1.2", "database": {"status": "unavailable", "version": null, "query_time_ms": null}}
```

У ошибок ввода текст `msg` от Pydantic остаётся английским. Интерфейс показывает как есть только текст ошибок вида `planner_format` и `planner_rule`. Для вида `missing` он пишет «Заполните поле», для всех остальных «Проверьте значение поля». Таблица ниже перечисляет виды, которые встречаются чаще других.

| Значение `type` | Что значит |
| --- | --- |
| `planner_format` | Сумма, дата или логин записаны не по шаблону. Текст в `msg` написан по-русски |
| `planner_rule` | Нарушено правило планера: занятый логин, чужой счёт, счёт в архиве, дата в будущем. Текст в `msg` написан по-русски |
| `missing` | Нет обязательного поля |
| `extra_forbidden` | Прислано лишнее поле |
| `int_type`, `bool_type`, `string_type` | Значение не того типа JSON |
| `greater_than`, `greater_than_equal`, `less_than_equal` | Число вне допустимых границ |
| `string_too_short`, `string_too_long`, `string_pattern_mismatch` | Строка не той длины или не того вида |
| `literal_error` | Значение не из списка допустимых |
| `date_from_datetime_parsing`, `int_parsing` | Дата не существует или параметр запроса не разбирается как число |

## 4. Ресурсы

В таблицах полей колонка «В запросе» показывает, можно ли прислать поле. «Обязательное» относится к созданию: в PATCH любое изменяемое поле можно не присылать. «Только в ответе» значит, что поле считает или задаёт сервер. Тип «сумма» описан в п. 4 раздела 1. Списки без страниц отсортированы по возрастанию `id`, если не сказано иное.

### 4.1. Проверка сервиса и токен CSRF

`GET /api/health` отвечает 200, когда база доступна, и 503, когда нет. Тело в обоих случаях одной формы.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `status` | строка | `ok` или `degraded` |
| `python_version`, `django_version` | строка | Версии на сервере |
| `database.status` | строка | `ok` или `unavailable` |
| `database.version` | строка или `null` | Версия PostgreSQL |
| `database.query_time_ms` | число или `null` | Время проверочного запроса в миллисекундах |

```json
{"status": "ok", "python_version": "3.14.9", "django_version": "6.1.2", "database": {"status": "ok", "version": "18.6", "query_time_ms": 9.2}}
```

`GET /api/auth/csrf` отвечает 204 без тела и ставит куку `csrftoken`. Интерфейс вызывает его перед первым изменяющим запросом и после ответа с кодом `csrf_failed`.

### 4.2. Пользователь и вход

| Поле | Тип | В запросе | Ограничения и смысл |
| --- | --- | --- | --- |
| `id` | целое | Только в ответе | Идентификатор |
| `username` | строка | Обязательное при регистрации и входе | При регистрации от 3 до 150 знаков: буквы, цифры и знаки `@`, `.`, `+`, `-`, `_`. Длина и знаки проверяются после нормализации NFKC, как в Django. Регистр учитывается. Уникален, после регистрации не меняется |
| `password` | строка | Обязательное при регистрации и входе | При регистрации от 8 до 128 знаков, проверяется валидаторами Django. При входе принимается любая непустая строка. В ответах пароля нет |
| `time_zone` | строка | Необязательное при регистрации, можно изменить | Имя часового пояса IANA, например `Asia/Yekaterinburg` |

1. Регистрация `POST /api/auth/register` сразу начинает сессию, отдельный вход после неё не нужен. Почта не запрашивается.
2. Занятый логин и слабый пароль дают 422 с указанием поля.
3. При регистрации пояс подставляет интерфейс из настроек браузера. Если пояс не передан или серверу неизвестен, берётся пояс сервера, ошибки нет.
4. Вход `POST /api/auth/login` принимает `username` и `password`. Неверная пара даёт 401 с кодом `invalid_credentials`.
5. Регистрация и вход при живой сессии выполняются как обычно и заменяют сессию.
6. Выход `POST /api/auth/logout` отвечает 204 и удаляет сессию. Тела у запроса нет, присланное тело сервер не читает.
7. Запрос `PATCH /api/auth/me` принимает только `time_zone`. Неизвестное имя пояса здесь даёт 422.

Запрос `POST /api/auth/register`:

```json
{"username": "anna", "password": "correct-horse-battery", "time_zone": "Asia/Yekaterinburg"}
```

Ответ 201. Такой же объект возвращают вход и оба запроса `/api/auth/me`:

```json
{"id": 1, "username": "anna", "time_zone": "Asia/Yekaterinburg"}
```

### 4.3. Счета

| Поле | Тип | В запросе | Ограничения и смысл |
| --- | --- | --- | --- |
| `id` | целое | Только в ответе | Идентификатор |
| `name` | строка | Обязательное | От 1 до 100 знаков |
| `kind` | строка | Только при создании, обязательное | `cash`, `card` или `savings`: наличные, карта, накопительный |
| `currency` | строка | Только при создании, необязательное | Код валюты из трёх заглавных букв, по умолчанию `RUB` |
| `initial_balance` | сумма | Необязательное | Начальный остаток, по умолчанию `"0.00"`. Допускается минус |
| `is_archived` | логическое | Только в PATCH | Счёт в архиве |
| `balance` | сумма | Только в ответе | Начальный остаток плюс доходы и зачисления минус расходы и списания. Может быть меньше нуля |
| `balance_rub` | сумма | Только в ответе, с шага 23 | Баланс в рублях по последнему курсу |
| `rate_date` | дата или `null` | Только в ответе, с шага 23 | Дата курса, по которому пересчитан баланс. У рублёвого счёта `null` |
| `created_at` | время | Только в ответе | Когда создан |

Ответ `GET /api/accounts` содержит все счета пользователя, включая архивные, и поле `total_balance`: сумму балансов всех этих счетов в рублях.

1. Тип и валюта задаются при создании и не меняются. До шага 23 принимается только `RUB`, после него любая валюта, по которой есть курс с датой не позже сегодняшнего дня пользователя.
2. Архивный счёт нельзя указать при создании операции, перевода, правила и цели и нельзя выбрать новым счётом при правке: такой запрос получает 422. Уже записанные операции архивного счёта можно править и удалять, переводы удалять.
3. Перенос счёта в архив выключает его правила (с шага 18). Возврат из архива правила обратно не включает.
4. Удаление счёта, на который ссылаются операции, переводы, правила или цель, отвечает 409 с кодом `account_in_use`. Такой счёт можно перенести в архив.

Запрос `POST /api/accounts`:

```json
{"name": "Карта", "kind": "card", "initial_balance": "15000.00"}
```

Ответ 201:

```json
{"id": 3, "name": "Карта", "kind": "card", "currency": "RUB", "initial_balance": "15000.00", "balance": "15000.00", "is_archived": false, "created_at": "2026-11-01T06:12:30.418Z"}
```

### 4.4. Категории

| Поле | Тип | В запросе | Ограничения и смысл |
| --- | --- | --- | --- |
| `id` | целое | Только в ответе | Идентификатор |
| `name` | строка | Обязательное | От 1 до 60 знаков |
| `kind` | строка | Только при создании, обязательное | `income` или `expense` |
| `is_common` | логическое | Только в ответе | `true` у общей категории |

Параметр `kind` у `GET /api/categories` оставляет категории одного вида. Список отсортирован по виду и названию.

1. Список содержит общие категории и свои.
2. Название уникально в пределах вида: оно не повторяет ни свою, ни общую категорию того же вида, иначе 422. Своя расходная категория может называться так же, как общая доходная.
3. Вид задаётся при создании и не меняется.
4. Общую категорию нельзя изменить или удалить: 403 с кодом `common_category`.
5. Категория, на которую ссылаются операции или правила, не удаляется: 409 с кодом `category_in_use`. Бюджеты удаляемой категории удаляются вместе с ней.

### 4.5. Операции

| Поле | Тип | В запросе | Ограничения и смысл |
| --- | --- | --- | --- |
| `id` | целое | Только в ответе | Идентификатор |
| `kind` | строка | Только при создании, обязательное | В запросе `income` или `expense`. В ответе бывает ещё `transfer_out` и `transfer_in` |
| `account_id` | целое | Обязательное | Свой счёт. Архивный счёт нельзя указать при создании и выбрать при смене счёта |

| `amount` | сумма | Обязательное | Больше нуля, в валюте счёта |
| `date` | дата | Обязательное | Дата операции, не позже сегодняшнего дня пользователя |
| `note` | строка | Необязательное | До 255 знаков, по умолчанию пустая |

| `recurring_rule_id` | целое или `null` | Только в ответе, с шага 18 | Правило, создавшее операцию |
| `exchange_rate` | объект или `null` | Только в ответе, с шага 23 | Зафиксированный курс: поля `date`, `nominal`, `value`. У рублёвой операции `null` |
| `amount_rub` | сумма | Только в ответе, с шага 23 | Сумма в рублях по зафиксированному курсу, округлённая до копейки |
| `created_at` | время | Только в ответе | Когда создана |

| Параметр `GET /api/operations` | Тип | Смысл |
| --- | --- | --- |
| `date_from`, `date_to` | дата | Границы периода, обе включительно. Можно передать одну из них |
| `account_id` | целое | Операции одного счёта |
| `category_id` | целое | Операции одной категории |
| `kind` | строка | Один из четырёх видов |
| `sort` | строка | `-date` (по умолчанию): сначала новые. `date`: сначала старые. При равной дате порядок задаёт `id` в том же направлении |
| `page`, `page_size` | целое | Страница и её размер |

2. Счёт должен быть своим, категория общей или своей и того же вида, что операция: иначе 422.
3. Вид операции после создания не меняется. Счёт можно сменить только на счёт в той же валюте.
4. Операцию, созданную правилом, можно менять и удалять как обычную. Заново правило её не создаст.
5. С шага 23 операция по счёту в валюте фиксирует последний курс с датой не позже даты операции. Курс фиксируется при создании и заново при смене даты. Если такого курса в базе нет, запрос отклоняется с кодом 422.

### 4.6. Переводы

| Поле | Тип | В запросе | Ограничения и смысл |
| --- | --- | --- | --- |
| `id` | целое | Только в ответе | Идентификатор |
| `from_account_id` | целое | Обязательное | Свой счёт списания, не в архиве |
| `to_account_id` | целое | Обязательное | Свой счёт зачисления, не в архиве, не совпадает со счётом списания |
| `amount_out` | сумма | Обязательное | Больше нуля, в валюте счёта списания |
| `amount_in` | сумма | Необязательное | Больше нуля, в валюте счёта зачисления. При одной валюте равна `amount_out` |
| `exchange_difference` | сумма | Только в ответе | Курсовая разница в рублях, может быть меньше нуля. До шага 23 всегда `"0.00"` |
| `date` | дата | Обязательное | Дата перевода, не позже сегодняшнего дня пользователя |
| `note` | строка | Необязательное | До 255 знаков, попадает в заметку обеих операций |
| `created_at` | время | Только в ответе | Когда создан |

Список `GET /api/transfers` постраничный: параметры `page` и `page_size`, сначала идут новые переводы.

1. Перевод и две его операции, списание и зачисление, создаются в одной транзакции.
2. Счета должны быть разными, своими и не в архиве: иначе 422.
3. При одной валюте поле `amount_in` можно не передавать. Значение, отличное от `amount_out`, даёт 422.
4. До шага 23 перевод между счетами в разных валютах отклоняется с кодом 422. С шага 23 для него обязательны обе суммы, а в `exchange_difference` записывается разница в рублях по зафиксированным курсам двух операций: больше нуля при потере на обмене, меньше нуля при выгоде.
5. Правдоподобие сумм сервер не проверяет: опечатка в сумме зачисления видна по большой разнице в ответе.
6. Перевод не редактируется: ошибочный удаляется и создаётся заново. Вместе с переводом удаляются обе его операции.

Запрос `POST /api/transfers`:

```json
{"from_account_id": 3, "to_account_id": 5, "amount_out": "5000.00", "date": "2026-11-15", "note": "В копилку"}
```

Ответ 201:

```json
{"id": 8, "from_account_id": 3, "to_account_id": 5, "amount_out": "5000.00", "amount_in": "5000.00", "exchange_difference": "0.00", "date": "2026-11-15", "note": "В копилку", "created_at": "2026-11-15T10:02:11.004Z"}
```

### 4.10. Периодические правила

| Поле | Тип | В запросе | Ограничения и смысл |
| --- | --- | --- | --- |
| `id` | целое | Только в ответе | Идентификатор |
| `name` | строка | Обязательное | От 1 до 100 знаков. Попадает в заметку созданной операции |
| `account_id` | целое | Обязательное | Свой счёт. Архивный счёт нельзя указать при создании и выбрать при смене счёта. Сменить счёт можно только на счёт в той же валюте |
| `category_id` | целое | Обязательное | Общая или своя категория. Её вид определяет вид операций правила. Сменить категорию можно только на категорию того же вида |
| `kind` | строка | Только в ответе | `income` или `expense`, вид категории правила |
| `amount` | сумма | Обязательное | Больше нуля, в валюте счёта |
| `frequency` | строка | Только при создании, обязательное | `monthly` или `weekly` |
| `day` | целое | Только при создании, обязательное | Для `monthly` от 1 до 31, для `weekly` от 1 до 7, где 1 значит понедельник |
| `start_date` | дата | Только при создании, обязательное | Начало действия |
| `end_date` | дата или `null` | Необязательное | Последний день действия, не раньше начала |
| `is_active` | логическое | Только в PATCH | Правило включено, при создании `true` |
| `next_date` | дата или `null` | Только в ответе | Следующая плановая дата. `null`, если правило выключено или срок вышел |
| `created_at` | время | Только в ответе | Когда создано |

1. Расписание (`frequency`, `day`, `start_date`) задаётся при создании и не меняется. Чтобы сменить день или периодичность, правило удаляется и создаётся новое, операции остаются. Если за текущий месяц или неделю начисление уже было, начало нового правила ставится на первый день следующего месяца или недели, иначе оно начислит второй раз за тот же период.
2. Правило на 29, 30 или 31 число в коротком месяце срабатывает в последний день месяца.
3. Первая плановая дата не раньше `start_date` и не раньше сегодняшнего дня пользователя: за прошедшие даты правило не начисляет.
4. Наступившая плановая дата применяется раз в час планировщиком и сразу в запросе, который создаёт правило, включает его или меняет у включённого правила название, счёт, категорию, сумму либо конец срока. В запросе изменения она применяется по прежним значениям. Операция создаётся с плановой датой в поле `date`.
5. Выключение правила и перенос его счёта в архив наступившие даты не применяют, даже если тот же запрос меняет другие поля. Выключенное правило не срабатывает. При включении не начисляются даты, прошедшие за время паузы, при продлении срока даты, прошедшие после прежнего конца срока: следующая плановая дата будет не раньше сегодняшнего дня.
6. Включить правило, счёт которого в архиве, нельзя: 409 с кодом `account_archived`.
7. Каждая плановая дата обрабатывается один раз. Удалённую операцию правило заново не создаёт, а пара «правило и плановая дата» в базе уникальна.
8. Удаление правила оставляет созданные им операции.

Запрос `POST /api/recurring-rules`:

```json
{"name": "Аренда квартиры", "account_id": 3, "category_id": 6, "amount": "35000.00", "frequency": "monthly", "day": 31, "start_date": "2026-12-01"}
```

Ответ 201:

```json
{"id": 1, "name": "Аренда квартиры", "account_id": 3, "category_id": 6, "kind": "expense", "amount": "35000.00", "frequency": "monthly", "day": 31, "start_date": "2026-12-01", "end_date": null, "is_active": true, "next_date": "2026-12-31", "created_at": "2026-11-18T09:20:44.731Z"}
```

### 4.11. Курсы валют

| Поле ответа | Тип | Смысл |
| --- | --- | --- |
| `currency` | строка | Код валюты из трёх заглавных букв |
| `date` | дата | Дата, на которую Банк России установил курс |
| `nominal` | целое | За сколько единиц валюты дан курс |
| `value` | строка | Рублей за номинал, четыре знака после точки |

| Параметр `GET /api/exchange-rates` | Тип | Смысл |
| --- | --- | --- |
| `date` | дата | Курсы на эту дату или последние до неё. Без параметра берутся последние загруженные |
| `currency` | строка | Курс одной валюты |

1. В ответе по одному курсу на валюту, список отсортирован по коду валюты. Рубля в списке нет.
2. Если на запрошенную дату и раньше курса нет, массив `items` пуст.
3. Названия валют интерфейс берёт из `Intl.DisplayNames`, сервер их не хранит.

Ответ `GET /api/exchange-rates?currency=CNY&date=2026-11-18` (значение условное):

```json
{
    "items": [
        {"currency": "CNY", "date": "2026-11-18", "nominal": 1, "value": "11.2345"}
    ]
}
```

## 5. Сверка с кодом

Django Ninja строит описание OpenAPI из схем и маршрутов. Его отдаёт `GET /api/openapi.json`, а страница `GET /api/docs` показывает маршруты и позволяет вызвать каждый из браузера. Расхождение кода с этим документом находят тесты.

1. Тест контракта читает таблицу раздела 3 и сравнивает её с описанием OpenAPI. У каждой строки с отметкой «да» в коде должен найтись маршрут с тем же методом, путём и кодом успеха. Каждый маршрут из кода должен стоять в таблице с отметкой «да».
2. По готовым строкам таблицы с отметкой входа параметризованный тест шлёт запрос с токеном, но без сессии и ждёт 401. Изменяющий запрос он повторяет с сессией, но без токена и ждёт 403. Новые маршруты попадают в эти проверки, как только в их строке появляется «да».
3. Коды 404, 409 и 422 каждого ресурса проверяют тесты его маршрутов: чужой объект, объект со ссылками, неверное поле, лишнее поле.
4. Тест лежит в `api/finance_planner/tests/test_contract.py`. Путь к этому файлу он берёт из переменной окружения `API_CONTRACT_PATH`, а без неё ищет `docs/api.md` от корня проекта. В контейнере `api` папка `docs/` подключена только для чтения как `/docs`, поэтому путь по умолчанию верен и там.

Отметка «да» в колонке «Готов» ставится в том же изменении, которое добавляет маршрут.
