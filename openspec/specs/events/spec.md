# events Specification

## Purpose

Мероприятия, на которые организатор собирает компанию: справочник категорий, создание, каталог, изменение и удаление мероприятий, запись и отказ от участия с соблюдением лимита мест и возрастного ограничения, управление списком участников.

## Requirements

### Requirement: Справочник категорий
Система SHALL хранить категории мероприятий в отдельном справочнике: `id` (целое число) и `name` (уникальная строка). Изначально справочник содержит «Настольные игры», «Прогулки», «Спорт», «Кино». Система SHALL по `GET /categories` возвращать все категории, упорядоченные по `id`.

#### Scenario: Получение категорий
- **WHEN** пользователь с заполненным профилем вызывает `GET /categories`
- **THEN** система отвечает 200 со списком категорий, в котором есть «Настольные игры», «Прогулки», «Спорт» и «Кино», у каждой есть `id` и `name`

#### Scenario: Черновик запрашивает категории
- **WHEN** пользователь с незаполненным профилем вызывает `GET /categories`
- **THEN** система отвечает 403 с кодом `profile_incomplete`

### Requirement: Представление мероприятия
Мероприятие SHALL содержать: `id` (UUID), `title`, `description`, `place`, `starts_at` (с часовым поясом), `duration_minutes` (или `null`), `created_at`, `category` (`id`, `name`), `max_participants`, `min_age`, `organizer` (`id`, `name`, `photo_url`, `telegram`), `photos` (список `{id}` по порядку, первое — основное; пустой, если фото нет), вычисляемые `participants_count`, `free_places`, `is_full` и `is_joined`. `organizer.telegram` MUST заполняться только записанному на мероприятие пользователю и администратору, остальным — `null`.

#### Scenario: Новое мероприятие
- **WHEN** организатор создаёт мероприятие с `max_participants` = 5
- **THEN** в ответе `participants_count` = 1, `free_places` = 4, `is_full` = false, `is_joined` = true, `created_at` — момент создания, `photos` — пустой список, а `organizer` содержит `id` и имя автора

#### Scenario: Заполненное мероприятие
- **WHEN** на мероприятие с `max_participants` = 2 кроме организатора записался ещё один участник
- **THEN** в ответе `free_places` = 0 и `is_full` = true

#### Scenario: Ответ не раскрывает контакты организатора
- **WHEN** пользователь, не записанный на мероприятие и не администратор, получает мероприятие организатора с указанным Telegram
- **THEN** `organizer.telegram` = `null`, а телефона и email организатора в ответе нет

#### Scenario: Telegram организатора для участника
- **WHEN** записанный участник или администратор получает то же мероприятие
- **THEN** `organizer.telegram` содержит Telegram организатора, а телефона и email в ответе нет

#### Scenario: Фото организатора
- **WHEN** у организатора задан `photo_url`
- **THEN** `organizer.photo_url` содержит эту ссылку для любого пользователя; без фото — `null`

#### Scenario: Фото мероприятия в ответе
- **WHEN** у мероприятия сохранены три фото и пользователь получает его через `GET /events/{id}` или в каталоге `GET /events`
- **THEN** `photos` содержит три элемента с `id` в сохранённом порядке, а содержимого файлов в ответе нет

### Requirement: Валидация полей мероприятия
Система SHALL отклонять с 422 некорректные значения: `title` — 1–100 символов после обрезки пробелов; `description` — 1–2000 символов после обрезки; `place` — 1–200 символов после обрезки; `starts_at` — дата и время с явным часовым поясом; `duration_minutes` — целое 1–1440 или `null`; `max_participants` — целое 2–100; `min_age` — одно из 0, 14, 16, 18; `category_id` — существующая категория.

#### Scenario: Лимит на границах
- **WHEN** организатор создаёт мероприятие с `max_participants` = 2, а затем другое с `max_participants` = 100
- **THEN** оба мероприятия создаются

#### Scenario: Лимит за границами
- **WHEN** организатор создаёт мероприятие с `max_participants` = 1 или 101
- **THEN** система отвечает 422 и мероприятие не создаётся

#### Scenario: Недопустимое возрастное ограничение
- **WHEN** организатор создаёт мероприятие с `min_age` = 12
- **THEN** система отвечает 422

#### Scenario: Несуществующая категория
- **WHEN** организатор создаёт мероприятие с `category_id`, которого нет в справочнике
- **THEN** система отвечает 422 с кодом `category_not_found`

#### Scenario: Время без часового пояса
- **WHEN** организатор передаёт `starts_at` = `2026-12-01T19:00:00` без смещения
- **THEN** система отвечает 422

#### Scenario: Пустое название
- **WHEN** организатор передаёт `title` из одних пробелов
- **THEN** система отвечает 422

### Requirement: Создание мероприятия
Система SHALL по `POST /events` создавать мероприятие, автором (организатором) которого становится текущий пользователь, и отвечать 201 с мероприятием. Создавать мероприятия MUST могут только пользователи с ролью `organizer`, остальным — 403. `starts_at` MUST быть строго позже текущего момента, иначе 422. В той же операции организатор MUST записываться участником мероприятия и занимать одно место.

#### Scenario: Успешное создание
- **WHEN** пользователь с ролью `organizer` создаёт мероприятие на завтра
- **THEN** система отвечает 201, а в списке участников мероприятия есть только сам организатор

#### Scenario: Дата в прошлом
- **WHEN** организатор создаёт мероприятие со `starts_at` на час раньше текущего момента
- **THEN** система отвечает 422 и мероприятие не создаётся

#### Scenario: Дата равна текущему моменту
- **WHEN** организатор создаёт мероприятие со `starts_at`, равным текущему моменту
- **THEN** система отвечает 422

#### Scenario: Пользователь без роли организатора
- **WHEN** пользователь без роли `organizer` вызывает `POST /events`
- **THEN** система отвечает 403 с кодом `forbidden`

### Requirement: Каталог мероприятий
Система SHALL по `GET /events` возвращать `items` и `total`. По умолчанию (`scope=all`, `period=upcoming`) — только предстоящие мероприятия (`starts_at` позже текущего момента) по возрастанию `starts_at`, при равенстве — по `id`. Фильтры: `category_id`, `from` (`starts_at` не раньше), `to` (`starts_at` раньше). Пагинация: `limit` 1–100, по умолчанию 20, `offset` от 0; недопустимые значения — 422. `total` — число с учётом фильтров, без пагинации.

#### Scenario: Только предстоящие
- **WHEN** в системе есть прошедшее мероприятие и два предстоящих
- **THEN** `GET /events` возвращает только два предстоящих, ближайшее первым, и `total` = 2

#### Scenario: Фильтр по категории
- **WHEN** пользователь вызывает `GET /events?category_id=<Спорт>`
- **THEN** в ответе только мероприятия категории «Спорт»

#### Scenario: Фильтр по диапазону дат
- **WHEN** пользователь вызывает `GET /events` с `from` = начало 1 декабря и `to` = начало 2 декабря
- **THEN** в ответе мероприятия, начинающиеся 1 декабря, а мероприятие, начинающееся ровно в начале 2 декабря, не попадает

#### Scenario: Пагинация
- **WHEN** есть 25 предстоящих мероприятий и пользователь вызывает `GET /events?limit=10&offset=20`
- **THEN** в ответе 5 мероприятий и `total` = 25

#### Scenario: Слишком большой лимит страницы
- **WHEN** пользователь вызывает `GET /events?limit=101`
- **THEN** система отвечает 422

### Requirement: Просмотр мероприятия
Система SHALL по `GET /events/{id}` возвращать мероприятие любому пользователю с заполненным профилем, в том числе уже начавшееся или прошедшее. Для несуществующего `id` система MUST отвечать 404.

#### Scenario: Просмотр чужого мероприятия
- **WHEN** пользователь, не записанный на мероприятие, вызывает `GET /events/{id}`
- **THEN** система отвечает 200 с мероприятием и `is_joined` = false

#### Scenario: Прошедшее мероприятие
- **WHEN** пользователь запрашивает мероприятие, которое уже прошло
- **THEN** система отвечает 200

#### Scenario: Несуществующее мероприятие
- **WHEN** пользователь запрашивает мероприятие с несуществующим `id`
- **THEN** система отвечает 404

### Requirement: Изменение мероприятия
Система SHALL по `PATCH /events/{id}` частично обновлять `title`, `description`, `place`, `starts_at`, `duration_minutes`, `category_id`, `max_participants` и `min_age` и возвращать обновлённое мероприятие. Изменять MUST могут только автор и администратор, остальным — 403; несуществующий `id` — 404. Очистить значением `null` можно только `duration_minutes`. Новое `starts_at` MUST быть позже текущего момента. Передача `organizer_id` или `id` MUST отклоняться с 422.

#### Scenario: Автор меняет место
- **WHEN** автор предстоящего мероприятия отправляет `PATCH` с новым `place`
- **THEN** система отвечает 200, место изменено, остальные поля прежние

#### Scenario: Администратор меняет чужое мероприятие
- **WHEN** администратор отправляет `PATCH` для мероприятия другого пользователя
- **THEN** система отвечает 200

#### Scenario: Посторонний пользователь
- **WHEN** пользователь, не являющийся автором или администратором, отправляет `PATCH`, в том числе будучи участником
- **THEN** система отвечает 403 и мероприятие не меняется

#### Scenario: Перенос в прошлое
- **WHEN** автор переносит `starts_at` на момент раньше текущего
- **THEN** система отвечает 422

#### Scenario: Попытка сменить организатора
- **WHEN** автор передаёт в `PATCH` поле `organizer_id`
- **THEN** система отвечает 422

### Requirement: Лимит не ниже числа участников
Система MUST отклонять с 409 и кодом `limit_below_participants` изменение `max_participants` до значения меньше текущего числа записанных участников. Уменьшение до значения, равного числу участников, допустимо. Изменение лимита и одновременная запись на мероприятие MUST выполняться так, чтобы число участников не превысило итоговый лимит.

#### Scenario: Лимит меньше числа участников
- **WHEN** на мероприятие записаны 4 человека и автор меняет `max_participants` на 3
- **THEN** система отвечает 409 с кодом `limit_below_participants` и лимит не меняется

#### Scenario: Лимит равен числу участников
- **WHEN** на мероприятие записаны 4 человека и автор меняет `max_participants` на 4
- **THEN** система отвечает 200, а мероприятие становится заполненным

#### Scenario: Уменьшение лимита одновременно с записью
- **WHEN** на мероприятии 3 участника и лимит 5, автор меняет лимит на 3, а другой пользователь одновременно записывается
- **THEN** выполняется ровно одна из операций: либо лимит 3 и участников 3, либо запись успешна и изменение лимита отклонено с 409

### Requirement: Удаление мероприятия
Система SHALL по `DELETE /events/{id}` безвозвратно удалять мероприятие вместе со всеми записями участников и фото и отвечать 204. Удалять MUST могут только автор и администратор, остальным — 403; несуществующий `id` — 404.

#### Scenario: Автор удаляет мероприятие
- **WHEN** автор удаляет предстоящее мероприятие с участниками
- **THEN** система отвечает 204, а последующий `GET /events/{id}` отвечает 404

#### Scenario: Участник пытается удалить
- **WHEN** записанный участник, не являющийся автором, вызывает `DELETE /events/{id}`
- **THEN** система отвечает 403 и мероприятие остаётся

#### Scenario: Фото удаляются вместе с мероприятием
- **WHEN** автор удаляет мероприятие с фото
- **THEN** запрос любого из его фото по прежнему `id` отвечает 404

### Requirement: Запрет действий после начала мероприятия
Когда мероприятие началось (`starts_at` не позже текущего момента), система MUST отклонять с 409 и кодом `event_started` изменение, удаление, запись, отказ от участия и удаление участника — в том числе для администратора. Проверка начала выполняется после проверки прав.

#### Scenario: Изменение начавшегося мероприятия
- **WHEN** автор отправляет `PATCH` для мероприятия, `starts_at` которого равен текущему моменту
- **THEN** система отвечает 409 с кодом `event_started`

#### Scenario: Администратор удаляет прошедшее мероприятие
- **WHEN** администратор вызывает `DELETE` для прошедшего мероприятия
- **THEN** система отвечает 409 с кодом `event_started` и мероприятие остаётся

#### Scenario: Запись на начавшееся мероприятие
- **WHEN** пользователь вызывает `POST /events/{id}/join` для начавшегося мероприятия со свободными местами
- **THEN** система отвечает 409 с кодом `event_started`

#### Scenario: Отказ от начавшегося мероприятия
- **WHEN** участник вызывает `POST /events/{id}/leave` после начала мероприятия
- **THEN** система отвечает 409 с кодом `event_started` и остаётся в списке участников

#### Scenario: Мероприятие за секунду до начала
- **WHEN** до `starts_at` остаётся одна секунда и пользователь записывается
- **THEN** запись выполняется

### Requirement: Запись на мероприятие
Система SHALL по `POST /events/{id}/join` записывать текущего пользователя участником и возвращать мероприятие. Записываться MUST могут только пользователи с ролью `participant`, остальным — 403. Несуществующий `id` — 404. Повторная запись уже записанного пользователя MUST отклоняться с 409 и кодом `already_joined`.

#### Scenario: Успешная запись
- **WHEN** пользователь подходящего возраста записывается на мероприятие со свободными местами
- **THEN** система отвечает 200, в ответе `is_joined` = true, а `participants_count` увеличился на 1

#### Scenario: Повторная запись
- **WHEN** уже записанный пользователь снова вызывает `POST /events/{id}/join`
- **THEN** система отвечает 409 с кодом `already_joined` и число участников не меняется

#### Scenario: Организатор записывается на своё мероприятие
- **WHEN** организатор вызывает `POST /events/{id}/join` для своего мероприятия
- **THEN** система отвечает 409 с кодом `already_joined`

#### Scenario: Пользователь без роли участника
- **WHEN** пользователь без роли `participant` вызывает `POST /events/{id}/join`
- **THEN** система отвечает 403 с кодом `forbidden`

### Requirement: Возрастное ограничение при записи
Система MUST отклонять запись с 403 и кодом `age_restricted`, если полных лет пользователя на текущую дату меньше `min_age` мероприятия. Возраст считается по дате рождения из профиля.

#### Scenario: Участник младше ограничения
- **WHEN** пользователю 17 лет и он записывается на мероприятие с `min_age` = 18
- **THEN** система отвечает 403 с кодом `age_restricted` и запись не создаётся

#### Scenario: Ограничению исполняется сегодня
- **WHEN** пользователю сегодня исполнилось 18 лет и он записывается на мероприятие с `min_age` = 18
- **THEN** запись выполняется

#### Scenario: Совершеннолетие наступит до мероприятия
- **WHEN** пользователю сегодня 17 лет, 18 исполнится до `starts_at`, а `min_age` = 18
- **THEN** система отвечает 403 с кодом `age_restricted`

#### Scenario: Мероприятие без ограничения
- **WHEN** мероприятие с `min_age` = 0 и пользователь любого возраста записывается
- **THEN** возраст не препятствует записи

### Requirement: Лимит мест при записи
Система MUST отклонять запись с 409 и кодом `event_full`, если на мероприятие уже записано `max_participants` человек, включая организатора. Проверка лимита и создание записи MUST выполняться атомарно: при одновременных запросах число участников никогда не превышает `max_participants`. Отказ от участия или удаление участника освобождает место.

#### Scenario: Запись на последнее место
- **WHEN** на мероприятии с лимитом 3 записаны 2 человека и пользователь записывается
- **THEN** запись выполняется, `is_full` = true

#### Scenario: Мест нет
- **WHEN** на мероприятии с лимитом 3 записаны 3 человека и пользователь записывается
- **THEN** система отвечает 409 с кодом `event_full`

#### Scenario: Одновременная запись на последнее место
- **WHEN** на мероприятии осталось одно место и несколько пользователей одновременно записываются
- **THEN** ровно один запрос успешен, остальные получают 409 с кодом `event_full`, участников ровно `max_participants`

#### Scenario: Место освободилось
- **WHEN** мероприятие заполнено, один участник отказался, а другой пользователь записывается
- **THEN** запись выполняется

### Requirement: Отказ от участия
Система SHALL по `POST /events/{id}/leave` удалять запись текущего пользователя и возвращать мероприятие. Если пользователь не записан, система MUST отвечать 409 с кодом `not_joined`. Организатор MUST NOT отказываться от своего мероприятия: 409 с кодом `organizer_cannot_leave`. Несуществующий `id` — 404. После отказа пользователь может записаться снова.

#### Scenario: Успешный отказ
- **WHEN** записанный участник вызывает `POST /events/{id}/leave`
- **THEN** система отвечает 200, `is_joined` = false, а число участников уменьшилось на 1

#### Scenario: Отказ без записи
- **WHEN** незаписанный пользователь вызывает `POST /events/{id}/leave`
- **THEN** система отвечает 409 с кодом `not_joined`

#### Scenario: Организатор пытается выйти
- **WHEN** организатор вызывает `POST /events/{id}/leave` для своего мероприятия
- **THEN** система отвечает 409 с кодом `organizer_cannot_leave` и остаётся участником

#### Scenario: Одновременный отказ
- **WHEN** один участник дважды одновременно вызывает `POST /events/{id}/leave`
- **THEN** один запрос успешен, второй получает 409 с кодом `not_joined`, число участников уменьшилось ровно на 1

### Requirement: Удаление участника организатором
Система SHALL по `POST /events/{id}/participants/{user_id}/remove` удалять запись указанного участника и возвращать мероприятие. Выполнять MUST могут только автор и администратор, остальным — 403; несуществующее мероприятие — 404. Если пользователь не записан — 404 с кодом `participant_not_found`. Удалить организатора нельзя: 409 с кодом `organizer_cannot_leave`. Удалённый участник может записаться снова.

#### Scenario: Организатор удаляет участника
- **WHEN** автор удаляет записанного участника предстоящего мероприятия
- **THEN** система отвечает 200, участника нет в списке, свободных мест стало на одно больше

#### Scenario: Удалённый записывается снова
- **WHEN** удалённый организатором участник снова вызывает `POST /events/{id}/join` при наличии мест
- **THEN** запись выполняется

#### Scenario: Участник пытается удалить другого
- **WHEN** записанный участник, не являющийся автором или администратором, удаляет другого участника
- **THEN** система отвечает 403 и запись не удаляется

#### Scenario: Удаление незаписанного пользователя
- **WHEN** автор удаляет пользователя, который не записан на мероприятие
- **THEN** система отвечает 404 с кодом `participant_not_found`

#### Scenario: Попытка удалить организатора
- **WHEN** администратор удаляет из участников организатора мероприятия
- **THEN** система отвечает 409 с кодом `organizer_cannot_leave`

### Requirement: Список участников
Система SHALL по `GET /events/{id}/participants` возвращать участников в порядке записи; каждый элемент содержит `id`, `name`, `photo_url` и `telegram` (`null`, если не задано) и MUST NOT содержать телефон и email. Список MUST быть доступен записанным участникам (включая организатора) и администратору, в том числе после начала мероприятия, поэтому Telegram участников виден только им. Остальным — 403, в том числе для несуществующего `id`; администратору для несуществующего `id` — 404.

#### Scenario: Участник смотрит список
- **WHEN** записанный участник вызывает `GET /events/{id}/participants`
- **THEN** система отвечает 200, первым в списке идёт организатор, у каждого элемента есть `id`, `name`, `photo_url` и `telegram`, но нет телефона и email

#### Scenario: Участник с Telegram
- **WHEN** у участника задан Telegram `@boris_k`, и другой записанный участник запрашивает список
- **THEN** элемент этого участника содержит `telegram` = `@boris_k`

#### Scenario: Участник без Telegram и фото
- **WHEN** у участника не заданы Telegram и фото
- **THEN** его элемент содержит `telegram` = `null` и `photo_url` = `null`

#### Scenario: Незаписанный пользователь
- **WHEN** пользователь, не записанный на мероприятие и не администратор, запрашивает список
- **THEN** система отвечает 403, контакты не раскрываются

#### Scenario: Несуществующее мероприятие для обычного пользователя
- **WHEN** пользователь, не являющийся администратором, запрашивает список участников несуществующего мероприятия
- **THEN** система отвечает 403, не раскрывая, существует ли мероприятие

#### Scenario: Несуществующее мероприятие для администратора
- **WHEN** администратор запрашивает список участников несуществующего мероприятия
- **THEN** система отвечает 404

#### Scenario: Бывший участник
- **WHEN** пользователь отказался от участия и запрашивает список
- **THEN** система отвечает 403

### Requirement: Доступ к ручкам мероприятий
Все ручки категорий и мероприятий SHALL требовать действующий access-токен и заполненный профиль: без токена — 401, с незаполненным профилем — 403 с кодом `profile_incomplete`.

#### Scenario: Каталог без токена
- **WHEN** клиент вызывает `GET /events` без заголовка авторизации
- **THEN** система отвечает 401

#### Scenario: Черновик записывается
- **WHEN** пользователь с незаполненным профилем вызывает `POST /events/{id}/join`
- **THEN** система отвечает 403 с кодом `profile_incomplete`

### Requirement: Мои мероприятия в каталоге
Система SHALL принимать в `GET /events` параметр `scope`: `all` (по умолчанию) — все мероприятия; `joined` — мероприятия, на которые записан текущий пользователь и организатором которых он не является; `organized` — мероприятия, автором которых он является. Остальные значения — 422. Фильтры, сортировка и пагинация применяются к выбранному набору.

#### Scenario: Участвую
- **WHEN** пользователь организует мероприятие A, записан на мероприятие B и не записан на C, все предстоящие, и вызывает `GET /events?scope=joined`
- **THEN** в ответе только B и `total` = 1

#### Scenario: Организую
- **WHEN** тот же пользователь вызывает `GET /events?scope=organized`
- **THEN** в ответе только A

#### Scenario: После отказа
- **WHEN** пользователь отказался от участия в мероприятии и вызывает `GET /events?scope=joined`
- **THEN** этого мероприятия нет в ответе

#### Scenario: Фильтр категории внутри своих
- **WHEN** пользователь вызывает `GET /events?scope=organized&category_id=<Спорт>`
- **THEN** в ответе только его мероприятия категории «Спорт»

#### Scenario: Неизвестный scope
- **WHEN** пользователь вызывает `GET /events?scope=mine`
- **THEN** система отвечает 422

### Requirement: Прошедшие мероприятия в каталоге
Система SHALL принимать в `GET /events` параметр `period`: `upcoming` (по умолчанию) — `starts_at` позже текущего момента, по возрастанию `starts_at`; `past` — `starts_at` не позже текущего момента, по убыванию `starts_at`, при равенстве — по `id`. `period=past` допустим только со `scope=joined` или `scope=organized`; со `scope=all` и для неизвестных значений — 422.

#### Scenario: Прошедшие свои мероприятия
- **WHEN** пользователь организовал мероприятия, прошедшие вчера и неделю назад, и одно предстоящее, и вызывает `GET /events?scope=organized&period=past`
- **THEN** в ответе два прошедших, вчерашнее первым, и `total` = 2

#### Scenario: Мероприятие в момент начала
- **WHEN** `starts_at` мероприятия равен текущему моменту
- **THEN** оно попадает в `period=past` и не попадает в `period=upcoming`

#### Scenario: Прошедшие в общем каталоге
- **WHEN** пользователь вызывает `GET /events?period=past` без `scope` или со `scope=all`
- **THEN** система отвечает 422

#### Scenario: Неизвестный period
- **WHEN** пользователь вызывает `GET /events?scope=joined&period=today`
- **THEN** система отвечает 422

### Requirement: Возрастной фильтр каталога
В общем каталоге (`scope=all`) система SHALL не возвращать мероприятия, у которых `min_age` больше полных лет текущего пользователя на текущую дату — то есть те, на которые он не сможет записаться. Во вкладках `scope=joined` и `scope=organized` возрастной фильтр не применяется. `total` считается с учётом фильтра.

#### Scenario: Подросток в общем каталоге
- **WHEN** пользователю 14 лет, а в каталоге есть предстоящие мероприятия 0+, 14+, 16+ и 18+
- **THEN** `GET /events` возвращает только 0+ и 14+, `total` = 2

#### Scenario: Ограничению исполняется сегодня
- **WHEN** пользователю сегодня исполнилось 18 лет
- **THEN** мероприятия 18+ попадают в общий каталог

#### Scenario: Своё мероприятие выше возраста
- **WHEN** 17-летний организатор создал мероприятие 18+
- **THEN** оно есть в `scope=organized`, но не в общем каталоге

### Requirement: Фильтр по свободным местам
Система SHALL принимать в `GET /events` параметр `min_free_places` (целое 1–100): возвращаются только мероприятия, у которых `max_participants` минус число записанных не меньше заданного. Фильтр применяется при любых `scope` и `period`, `total` считается с его учётом. Значения вне диапазона — 422.

#### Scenario: Граница свободных мест
- **WHEN** у мероприятия лимит 5 и записано 3 человека, а пользователь вызывает `GET /events?min_free_places=2`
- **THEN** мероприятие есть в ответе, а при `min_free_places=3` — нет

#### Scenario: Заполненные мероприятия скрыты
- **WHEN** пользователь вызывает `GET /events?min_free_places=1`
- **THEN** в ответе нет мероприятий без свободных мест

#### Scenario: Недопустимое значение
- **WHEN** пользователь вызывает `GET /events?min_free_places=0` или `min_free_places=101`
- **THEN** система отвечает 422

### Requirement: Ограничения набора фото мероприятия
У мероприятия SHALL быть от 0 до 10 фото; порядок задаётся при сохранении, первое фото — основное. Каждый файл MUST быть JPEG, PNG или WebP не больше 2 МБ (2 097 152 байт). Тип определяется по содержимому файла, а не по имени или заявленному типу. Нарушение — 422 с кодом `too_many_photos`, `photo_too_large` или `photo_invalid`; в ошибке о файле указывается номер файла в запросе.

#### Scenario: Десять фото
- **WHEN** автор сохраняет набор из 10 фото
- **THEN** система отвечает 200 и у мероприятия 10 фото

#### Scenario: Одиннадцать фото
- **WHEN** автор сохраняет набор из 11 фото
- **THEN** система отвечает 422 с кодом `too_many_photos`, набор фото не меняется

#### Scenario: Файл ровно 2 МБ
- **WHEN** автор загружает JPEG размером ровно 2 097 152 байт
- **THEN** фото сохраняется

#### Scenario: Файл больше 2 МБ
- **WHEN** автор загружает файл размером 2 097 153 байт
- **THEN** система отвечает 422 с кодом `photo_too_large` и номером этого файла, набор фото не меняется

#### Scenario: Не картинка с расширением jpg
- **WHEN** автор загружает текстовый файл с именем `photo.jpg` и типом `image/jpeg`
- **THEN** система отвечает 422 с кодом `photo_invalid`

#### Scenario: Неподдерживаемый формат
- **WHEN** автор загружает корректный GIF
- **THEN** система отвечает 422 с кодом `photo_invalid`

### Requirement: Получение фото мероприятия
Система SHALL по `GET /events/{id}/photos/{photo_id}` отдавать содержимое фото с его типом (`image/jpeg`, `image/png` или `image/webp`) любому пользователю, которому доступен просмотр мероприятия, в том числе после его начала. Фото с заданным `id` никогда не меняется, поэтому ответ MUST разрешать браузеру хранить его в личном кеше бессрочно и MUST NOT разрешать общим кешам. Если мероприятия нет или фото ему не принадлежит — 404.

#### Scenario: Пользователь открывает фото
- **WHEN** незаписанный пользователь с заполненным профилем запрашивает фото мероприятия
- **THEN** система отвечает 200 с содержимым файла, типом картинки и заголовком `Cache-Control: private, max-age=31536000, immutable`

#### Scenario: Фото прошедшего мероприятия
- **WHEN** пользователь запрашивает фото мероприятия, которое уже прошло
- **THEN** система отвечает 200

#### Scenario: Фото другого мероприятия
- **WHEN** пользователь запрашивает `photo_id` мероприятия A по адресу мероприятия B
- **THEN** система отвечает 404

#### Scenario: Без токена
- **WHEN** клиент запрашивает фото без заголовка авторизации
- **THEN** система отвечает 401 и не отдаёт файл

### Requirement: Замена набора фото мероприятия
Система SHALL по `PUT /events/{id}/photos` (multipart) заменять набор фото итоговым упорядоченным списком из уже сохранённых фото этого мероприятия и новых файлов и возвращать мероприятие. Сохранённые фото, которых нет в списке, удаляются; оставшиеся сохраняют свой `id`, новые получают новые `id`. Ссылка на чужое или несуществующее фото, повтор одного фото или неиспользованный файл — 422 `photo_list_invalid`.

#### Scenario: Добавление к существующим
- **WHEN** у мероприятия фото A и B, а автор сохраняет список A, B и новый файл
- **THEN** система отвечает 200, `photos` содержит A, B и новое фото в этом порядке

#### Scenario: Смена основного фото
- **WHEN** у мероприятия фото A, B, C, а автор сохраняет список C, A, B
- **THEN** основным становится C, `id` всех трёх фото не меняются

#### Scenario: Удаление всех фото
- **WHEN** автор сохраняет пустой список
- **THEN** у мероприятия нет фото, а запрос прежних фото отвечает 404

#### Scenario: Ссылка на фото другого мероприятия
- **WHEN** автор передаёт в списке `id` фото другого мероприятия
- **THEN** система отвечает 422 с кодом `photo_list_invalid`, набор фото не меняется

#### Scenario: Ошибка в одном из файлов
- **WHEN** автор сохраняет список из сохранённого фото и двух новых файлов, второй из которых больше 2 МБ
- **THEN** система отвечает 422 с кодом `photo_too_large`, ни один новый файл не сохраняется, сохранённое фото остаётся

### Requirement: Права на изменение фото мероприятия
Изменять набор фото SHALL могут только автор мероприятия и администратор, остальным — 403; для несуществующего мероприятия — 404. После начала мероприятия изменение MUST отклоняться с 409 и кодом `event_started`, в том числе для администратора. Права и начало мероприятия проверяются до разбора загруженных файлов.

#### Scenario: Администратор меняет фото чужого мероприятия
- **WHEN** администратор сохраняет набор фото мероприятия другого пользователя
- **THEN** система отвечает 200

#### Scenario: Участник пытается изменить фото
- **WHEN** записанный участник, не являющийся автором или администратором, вызывает `PUT /events/{id}/photos`, в том числе с некорректным файлом
- **THEN** система отвечает 403 и набор фото не меняется

#### Scenario: Изменение фото начавшегося мероприятия
- **WHEN** автор вызывает `PUT /events/{id}/photos` для мероприятия, `starts_at` которого равен текущему моменту
- **THEN** система отвечает 409 с кодом `event_started`

#### Scenario: Изменение фото за секунду до начала
- **WHEN** до `starts_at` остаётся одна секунда и автор сохраняет набор фото
- **THEN** изменение выполняется

#### Scenario: Несуществующее мероприятие
- **WHEN** автор вызывает `PUT /events/{id}/photos` для несуществующего `id`
- **THEN** система отвечает 404

### Requirement: Обработка загруженных фото
Перед сохранением система SHALL удалять из файла метаданные (EXIF и подобные, включая координаты съёмки) и поворачивать изображение по метке ориентации, чтобы без метаданных снимок отображался так же, как до загрузки. Формат файла (JPEG, PNG, WebP) MUST сохраняться.

#### Scenario: Снимок с геопозицией
- **WHEN** автор загружает JPEG с координатами съёмки в EXIF
- **THEN** отдаваемый файл — JPEG без EXIF и без координат

#### Scenario: Повёрнутый снимок
- **WHEN** автор загружает JPEG 400×300 с меткой ориентации «повернуть на 90°»
- **THEN** отдаваемый файл имеет размер 300×400 и не содержит метки ориентации

### Requirement: Одновременное изменение фото
Замена набора фото MUST выполняться атомарно и по очереди с другими изменениями того же мероприятия: при одновременных запросах итоговый набор совпадает с результатом одного из них целиком, а у мероприятия никогда не бывает больше 10 фото.

#### Scenario: Два одновременных сохранения
- **WHEN** у мероприятия 4 фото, а автор и администратор одновременно сохраняют наборы, каждый — из этих 4 и 6 новых файлов
- **THEN** оба запроса успешны и выполняются по очереди, у мероприятия ровно 10 фото — набор одного из запросов целиком

#### Scenario: Сохранение вместе с удалением мероприятия
- **WHEN** автор сохраняет набор фото, а администратор одновременно удаляет мероприятие
- **THEN** мероприятие удалено вместе со всеми фото, а запрос сохранения либо выполнился до удаления, либо получил 404
