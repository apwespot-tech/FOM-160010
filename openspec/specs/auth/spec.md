# auth Specification

## Purpose

Вход и регистрация пользователей по одноразовому коду, привязанному к номеру телефона, выдача и отзыв токенов, назначение ролей и защита ручек API от неавторизованного доступа.

## Requirements

### Requirement: Запрос кода входа
Система SHALL по `POST /auth/code` с номером телефона нормализовать номер к формату E.164, создать одноразовый код из 6 цифр со сроком действия 5 минут и сохранить его. Создание нового кода MUST делать недействительными все прежние неиспользованные коды этого номера. Ответ не содержит код. Регистрация отдельно не требуется: код можно запросить для любого корректного номера.

#### Scenario: Успешный запрос кода
- **WHEN** клиент отправляет `POST /auth/code` с номером `8 (999) 123-45-67`
- **THEN** система отвечает 200 со временем действия кода в секундах, а для номера `+79991234567` в БД есть действующий код из 6 цифр

#### Scenario: Некорректный номер
- **WHEN** клиент отправляет `POST /auth/code` с номером `12ab`
- **THEN** система отвечает 422 и код не создаётся

#### Scenario: Новый код отменяет предыдущий
- **WHEN** для номера уже есть действующий код и интервал повторного запроса истёк, а клиент запрашивает код снова
- **THEN** создаётся новый код, а прежний код больше не принимается при проверке

### Requirement: Ограничение частоты запроса кода
Система SHALL принимать запрос нового кода для одного номера не чаще одного раза в 60 секунд. Интервал MUST отсчитываться от создания последнего кода этого номера, который ещё не был успешно проверен; успешно проверенный код повторному запросу не мешает. Более ранний запрос MUST отклоняться с кодом 429 и указанием, через сколько секунд можно повторить.

#### Scenario: Повторный запрос раньше 60 секунд
- **WHEN** код для номера запрошен 30 секунд назад, не был проверен, и клиент запрашивает код снова
- **THEN** система отвечает 429 с оставшимся временем ожидания и действующий код не меняется

#### Scenario: Повторный запрос ровно через 60 секунд
- **WHEN** с момента предыдущего запроса прошло 60 секунд
- **THEN** система создаёт новый код и отвечает 200

#### Scenario: Повторный вход сразу после выхода
- **WHEN** пользователь 20 секунд назад запросил код, успешно его проверил, вышел и запрашивает код снова
- **THEN** система создаёт новый код и отвечает 200, а тестовая ручка возвращает этот новый код

#### Scenario: Код отклонён по попыткам или сроку
- **WHEN** код запрошен 30 секунд назад и стал недействительным после пяти неверных попыток, а клиент запрашивает новый
- **THEN** система отвечает 429: интервал отсчитывается от непроверенного кода, даже если он уже недействителен

#### Scenario: Одновременные запросы после успешного входа
- **WHEN** после успешной проверки кода два запроса нового кода для того же номера приходят одновременно
- **THEN** ровно один создаёт код и получает 200, второй получает 429

### Requirement: Тестовое получение кода
Система SHALL предоставлять `GET /auth/test/code?phone=<номер>`, возвращающий действующий код для номера, только когда тестовые ручки включены настройкой окружения. При выключенной настройке ручка MUST отвечать 404, как несуществующая.

#### Scenario: Получение кода при включённой настройке
- **WHEN** тестовые ручки включены и для номера есть действующий код
- **THEN** система отвечает 200 и возвращает этот код

#### Scenario: Нет действующего кода
- **WHEN** тестовые ручки включены, а для номера нет действующего кода (не запрашивался, истёк, использован или отменён)
- **THEN** система отвечает 404

#### Scenario: Настройка выключена
- **WHEN** тестовые ручки выключены и клиент вызывает `GET /auth/test/code`
- **THEN** система отвечает 404 и код не раскрывается

### Requirement: Проверка кода и выдача токенов
Система SHALL по `POST /auth/verify` с телефоном и кодом проверить, что код действующий, и выдать access-токен (срок 15 минут) и refresh-токен (срок 30 дней). Успешно проверенный код MUST становиться использованным и больше не приниматься. Неверный, истёкший, использованный или отменённый код MUST отклоняться с 400 без выдачи токенов.

#### Scenario: Верный код
- **WHEN** клиент отправляет действующий код для своего номера
- **THEN** система отвечает 200 с access-токеном, refresh-токеном и сроками их действия

#### Scenario: Повторное использование кода
- **WHEN** клиент повторно отправляет уже успешно проверенный код
- **THEN** система отвечает 400 и токены не выдаются

#### Scenario: Истёкший код
- **WHEN** с момента создания кода прошло больше 5 минут
- **THEN** система отвечает 400 даже при совпадении цифр

#### Scenario: Код на границе срока
- **WHEN** код отправлен до истечения 5 минут с момента создания
- **THEN** код принимается

#### Scenario: Одновременная проверка одного кода
- **WHEN** два запроса с одним и тем же действующим кодом приходят одновременно
- **THEN** ровно один запрос получает токены, второй получает 400

### Requirement: Ограничение попыток ввода кода
Система SHALL допускать не более 5 неверных попыток проверки на один код. После пятой неверной попытки код MUST становиться недействительным, и даже верный ввод этого кода отклоняется с 400.

#### Scenario: Пятая неверная попытка
- **WHEN** клиент пятый раз отправляет неверный код для номера
- **THEN** система отвечает 400, и последующая отправка верного кода тоже отклоняется

#### Scenario: Верный код после четырёх ошибок
- **WHEN** после четырёх неверных попыток клиент отправляет верный код
- **THEN** система выдаёт токены

### Requirement: Создание пользователя при первом входе
При успешной проверке кода для номера, которому не соответствует ни один пользователь, система SHALL создать пользователя с этим телефоном, ролями `participant` и `organizer` и незаполненным профилем. Для существующего пользователя новый не создаётся. Одновременные первые входы с одного номера MUST приводить к одному пользователю.

#### Scenario: Первый вход
- **WHEN** номер ранее не использовался и код проверен успешно
- **THEN** создаётся пользователь с ролями `participant` и `organizer`, а его профиль помечен как незаполненный

#### Scenario: Повторный вход
- **WHEN** пользователь с этим номером уже существует и код проверен успешно
- **THEN** токены выдаются для существующего пользователя, новый пользователь не создаётся

### Requirement: Роль администратора по настройке окружения
Система SHALL назначать роль `admin` пользователю, чей телефон входит в список администраторов из настройки окружения, и снимать её, если телефона в списке нет. Роль MUST синхронизироваться при каждом успешном `POST /auth/verify` и `POST /auth/refresh`.

#### Scenario: Вход администратора
- **WHEN** пользователь с телефоном из списка администраторов проверяет код
- **THEN** у него есть роли `participant`, `organizer` и `admin`

#### Scenario: Телефон удалён из списка
- **WHEN** телефон администратора убран из списка и пользователь обновляет токены
- **THEN** роль `admin` снимается, и новые токены её не содержат

### Requirement: Обновление токенов
Система SHALL по `POST /auth/refresh` с действующим refresh-токеном выдать новую пару токенов и сделать предъявленный refresh-токен недействительным. Истёкший, отозванный, уже использованный или неизвестный refresh-токен MUST отклоняться с 401.

#### Scenario: Успешное обновление
- **WHEN** клиент предъявляет действующий refresh-токен
- **THEN** система отвечает 200 с новой парой токенов

#### Scenario: Повторное использование refresh-токена
- **WHEN** клиент повторно предъявляет refresh-токен, который уже был обменян
- **THEN** система отвечает 401

#### Scenario: Истёкший refresh-токен
- **WHEN** с момента выдачи refresh-токена прошло больше 30 дней
- **THEN** система отвечает 401

#### Scenario: Одновременное обновление одним токеном
- **WHEN** два запроса с одним и тем же действующим refresh-токеном приходят одновременно
- **THEN** ровно один получает новую пару, второй получает 401

### Requirement: Выход
Система SHALL по `POST /auth/logout` с refresh-токеном отозвать этот токен и ответить 204. Повторный выход с тем же или неизвестным токеном MUST также отвечать 204, не раскрывая состояние токена.

#### Scenario: Выход
- **WHEN** клиент выходит, предъявив действующий refresh-токен
- **THEN** система отвечает 204, и последующий `POST /auth/refresh` с этим токеном получает 401

#### Scenario: Повторный выход
- **WHEN** клиент повторно выходит с уже отозванным токеном
- **THEN** система отвечает 204

### Requirement: Защита ручек access-токеном
Все ручки, кроме `POST /auth/code`, `GET /auth/test/code`, `POST /auth/verify`, `POST /auth/refresh` и `POST /auth/logout`, SHALL требовать действующий access-токен в заголовке `Authorization: Bearer`. Отсутствующий, некорректный или истёкший токен MUST отклоняться с 401.

#### Scenario: Запрос без токена
- **WHEN** клиент вызывает `GET /profile` без заголовка авторизации
- **THEN** система отвечает 401

#### Scenario: Истёкший access-токен
- **WHEN** с момента выдачи access-токена прошло больше 15 минут
- **THEN** защищённая ручка отвечает 401

### Requirement: Ограничение доступа при незаполненном профиле
Пока профиль пользователя не заполнен, система SHALL разрешать ему ручки просмотра: свой профиль (`GET`, `PATCH /profile`), категории и их картинки, города, каталог и просмотр мероприятия, фото мероприятий, картинки профилей. На остальные защищённые ручки — действия с мероприятиями и их фото, список и исключение участников, загрузку и удаление аватара и обложки, чужие профили — система MUST отвечать 403 с кодом ошибки `profile_incomplete`.

#### Scenario: Черновик обращается к чужому профилю
- **WHEN** пользователь с незаполненным профилем вызывает `GET /profile/{id}`
- **THEN** система отвечает 403 с кодом `profile_incomplete`

#### Scenario: Черновик смотрит каталог
- **WHEN** пользователь с незаполненным профилем вызывает `GET /events`, `GET /events/{id}`, `GET /categories` и `GET /cities`
- **THEN** система отвечает 200 на каждый запрос

#### Scenario: Черновик записывается или создаёт мероприятие
- **WHEN** пользователь с незаполненным профилем вызывает `POST /events/{id}/join` или `POST /events`
- **THEN** система отвечает 403 с кодом `profile_incomplete`, запись и мероприятие не создаются

#### Scenario: Черновик заполняет профиль
- **WHEN** пользователь с незаполненным профилем вызывает `PATCH /profile` с именем и датой рождения
- **THEN** запрос выполняется, и после этого ограничение снимается

#### Scenario: Заполнено только имя
- **WHEN** пользователь задал имя, но не дату рождения, и вызывает `POST /events/{id}/join`
- **THEN** система отвечает 403 с кодом `profile_incomplete`
