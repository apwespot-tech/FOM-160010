# notifications Specification

## Purpose

Уведомления пользователя внутри приложения: какие действия с мероприятиями и участием их порождают и кому они приходят, напоминание об открытии окна отзывов, список уведомлений, число непрочитанных и отметка прочитанными.

## Requirements

### Requirement: Уведомление об изменении мероприятия
Успешное изменение мероприятия SHALL создавать уведомление `event_changed` каждому записанному на него пользователю, кроме совершившего изменение, если новое значение отличается от прежнего хотя бы в одном из полей `starts_at`, `duration_minutes`, `city_id`, `place`, `title`. Уведомление MUST перечислять в `changed_fields` все изменившиеся поля из этого набора. Изменение только других полей или передача прежних значений уведомлений MUST NOT создавать.

#### Scenario: Перенос времени и места
- **WHEN** организатор мероприятия с тремя другими участниками меняет `starts_at` и `place`
- **THEN** каждый из трёх участников получает `event_changed` с `changed_fields` = `["starts_at", "place"]`, организатор уведомления не получает

#### Scenario: Изменение описания
- **WHEN** организатор меняет только `description` и `max_participants`
- **THEN** уведомления не создаются

#### Scenario: Прежнее значение
- **WHEN** организатор отправляет `PATCH` с `place`, равным текущему
- **THEN** уведомления не создаются

#### Scenario: Изменение названия
- **WHEN** организатор меняет название «Мафия» на «Мафия в пятницу»
- **THEN** участники получают `event_changed` с `changed_fields` = `["title"]` и названием мероприятия «Мафия в пятницу»

#### Scenario: Изменяет администратор
- **WHEN** администратор, не записанный на мероприятие, меняет `starts_at`
- **THEN** уведомление получают все записанные, включая организатора

#### Scenario: Изменение отклонено
- **WHEN** изменение отклонено с ошибкой, например 409 `limit_below_participants` при одновременной смене `place`
- **THEN** уведомления не создаются

#### Scenario: Мероприятие без других участников
- **WHEN** организатор меняет время мероприятия, на которое записан только он
- **THEN** уведомления не создаются

### Requirement: Уведомление об удалении мероприятия
Успешное удаление мероприятия SHALL создавать уведомление `event_deleted` каждому записанному на него пользователю, кроме удалившего. Уведомление MUST содержать название мероприятия на момент удаления.

#### Scenario: Организатор удаляет мероприятие
- **WHEN** организатор удаляет мероприятие «Прогулка» с двумя другими участниками
- **THEN** оба участника получают `event_deleted` с названием «Прогулка» и `event.id` = `null`, организатор уведомления не получает

#### Scenario: Удаляет администратор
- **WHEN** администратор удаляет чужое мероприятие
- **THEN** уведомление получают все записанные, включая организатора

#### Scenario: Удаление отклонено
- **WHEN** удаление начавшегося мероприятия отклонено с 409 `event_started`
- **THEN** уведомления не создаются

### Requirement: Уведомление об исключении участника
Успешное исключение участника SHALL создавать уведомление `participant_removed` исключённому. Если исключает не организатор, а администратор, такое же уведомление MUST получать и организатор. Уведомление MUST указывать исключённого участника.

#### Scenario: Организатор исключает участника
- **WHEN** организатор исключает участника Анну
- **THEN** Анна получает `participant_removed`, где `participant` — она сама; организатор уведомления не получает

#### Scenario: Исключает администратор
- **WHEN** администратор исключает Анну из чужого мероприятия
- **THEN** `participant_removed` с `participant` = Анна получают Анна и организатор

#### Scenario: Исключение незаписанного
- **WHEN** исключение отклонено с 404 `participant_not_found`
- **THEN** уведомления не создаются

### Requirement: Уведомления организатору о записи и отказе
Успешная запись на мероприятие SHALL создавать организатору уведомление `participant_joined`, успешный отказ от участия — `participant_left`. Уведомление MUST указывать участника. Каждое действие создаёт отдельное уведомление, уведомления не объединяются и не отменяют друг друга.

#### Scenario: Запись
- **WHEN** Олег записывается на мероприятие
- **THEN** организатор получает `participant_joined` с `participant` = Олег

#### Scenario: Запись и отказ подряд
- **WHEN** Олег записывается и сразу отказывается
- **THEN** у организатора два уведомления: `participant_joined` и `participant_left`

#### Scenario: Запись отклонена
- **WHEN** запись отклонена с 409 `event_full`
- **THEN** уведомления не создаются

#### Scenario: Одновременная запись на последнее место
- **WHEN** два пользователя одновременно записываются на последнее свободное место
- **THEN** организатор получает ровно одно `participant_joined` — о том, чья запись выполнена

### Requirement: Уведомления вместе с действием
Уведомления о действиях с мероприятием и участием SHALL сохраняться атомарно с самим действием: если действие выполнено, все его уведомления созданы; если отклонено или не завершилось, ни одного уведомления нет.

#### Scenario: Сбой при сохранении
- **WHEN** сохранение записи на мероприятие завершается ошибкой базы данных
- **THEN** ни записи, ни уведомления организатору нет

### Requirement: Напоминание об окне отзывов
Когда наступает `starts_at` + 24 часа, система SHALL создавать уведомление `review_reminder` каждому записанному на мероприятие пользователю, у которого на нём есть хотя бы один другой записанный. Напоминание по одному мероприятию MUST создаваться пользователю не больше одного раза и не создаваться после закрытия окна отзывов (`starts_at` + 8 суток). Допускается задержка создания не больше интервала фонового процесса.

#### Scenario: Окно открылось
- **WHEN** у мероприятия с организатором и двумя участниками наступает `starts_at` + 24 часа
- **THEN** все трое получают по одному `review_reminder`

#### Scenario: Окно ещё не открылось
- **WHEN** до `starts_at` + 24 часа остаётся минута
- **THEN** напоминания не создаются

#### Scenario: Ровно в момент открытия
- **WHEN** фоновый процесс выполняется ровно в `starts_at` + 24 часа
- **THEN** напоминания создаются

#### Scenario: Повторный прогон
- **WHEN** фоновый процесс выполняется ещё раз, в том числе одновременно с другим прогоном
- **THEN** новых напоминаний по этому мероприятию не появляется, у каждого пользователя одно

#### Scenario: Единственный участник
- **WHEN** окно открылось у мероприятия, на которое записан только организатор
- **THEN** напоминание не создаётся

#### Scenario: Окно уже закрыто
- **WHEN** фоновый процесс не работал и впервые выполняется в `starts_at` + 8 суток
- **THEN** напоминания по этому мероприятию не создаются

### Requirement: Представление уведомления
Уведомление SHALL содержать: `id`, `type` (`event_changed`, `event_deleted`, `participant_removed`, `participant_joined`, `participant_left`, `review_reminder`), `created_at`, `read`, `event` (`id` и `title`), `participant` (`id` и `name`) для `participant_removed`, `participant_joined` и `participant_left`, иначе `null`, и `changed_fields` для `event_changed`, иначе `null`. `event.title` — название на момент создания уведомления, `participant.name` — текущее имя пользователя.

#### Scenario: Уведомление о записи
- **WHEN** организатор получает уведомление о записи Олега
- **THEN** в нём `type` = `participant_joined`, `participant` = `{id, name: "Олег"}`, `changed_fields` = `null`, `read` = `false`

#### Scenario: Название изменили позже
- **WHEN** после уведомления о записи организатор переименовал мероприятие
- **THEN** в прежнем уведомлении остаётся прежнее название

### Requirement: Уведомления после удаления мероприятия
Уведомления SHALL сохраняться при удалении мероприятия: `event.id` становится `null`, название остаётся прежним.

#### Scenario: Мероприятие удалено после записи
- **WHEN** у организатора есть уведомление о записи на мероприятие, и мероприятие удалено
- **THEN** уведомление остаётся в списке с `event.id` = `null` и прежним названием

### Requirement: Список уведомлений
`GET /notifications` SHALL возвращать уведомления текущего пользователя — не больше 20 последних, от новых к старым — и `unread_count` — число всех его непрочитанных уведомлений. Чужие уведомления MUST NOT возвращаться никому, в том числе администратору.

#### Scenario: Больше 20 уведомлений
- **WHEN** у пользователя 25 уведомлений, из них 22 непрочитанных
- **THEN** ответ содержит 20 самых новых уведомлений и `unread_count` = 22

#### Scenario: Ровно 20 уведомлений
- **WHEN** у пользователя 20 уведомлений
- **THEN** ответ содержит все 20

#### Scenario: Нет уведомлений
- **WHEN** у пользователя нет уведомлений
- **THEN** ответ содержит пустой список и `unread_count` = 0

#### Scenario: Только свои
- **WHEN** администратор запрашивает уведомления
- **THEN** в ответе только уведомления, адресованные ему

### Requirement: Число непрочитанных
`GET /notifications/unread-count` SHALL возвращать `unread_count` — число непрочитанных уведомлений текущего пользователя — без самих уведомлений.

#### Scenario: Новое уведомление
- **WHEN** у пользователя 0 непрочитанных, и на его мероприятие кто-то записался
- **THEN** `GET /notifications/unread-count` возвращает `unread_count` = 1

### Requirement: Отметка уведомлений прочитанными
`POST /notifications/read` с полем `up_to` (момент времени) SHALL отмечать прочитанными все непрочитанные уведомления текущего пользователя с `created_at` не позже `up_to` и отвечать 204. Уведомления, созданные позже `up_to`, MUST оставаться непрочитанными. Повторная отметка не меняет уже прочитанные.

#### Scenario: Отметка показанных
- **WHEN** пользователь отмечает прочитанными уведомления с `up_to`, равным `created_at` самого нового из полученных
- **THEN** все его уведомления, включая самое новое, прочитаны, `unread_count` = 0

#### Scenario: Уведомление пришло после показа
- **WHEN** после получения списка пришло новое уведомление, а клиент отметил прочитанными с прежним `up_to`
- **THEN** новое уведомление остаётся непрочитанным, `unread_count` = 1

#### Scenario: Повторная отметка
- **WHEN** пользователь отправляет ту же отметку дважды
- **THEN** оба раза ответ 204, состояние уведомлений не меняется

#### Scenario: Без up_to
- **WHEN** запрос отправлен без поля `up_to`
- **THEN** система отвечает 422

### Requirement: Доступ к ручкам уведомлений
Все ручки уведомлений SHALL требовать действующий access-токен: без токена — 401. Пользователю с незаполненным профилем ручки уведомлений MUST быть доступны.

#### Scenario: Без токена
- **WHEN** клиент вызывает `GET /notifications/unread-count` без заголовка авторизации
- **THEN** система отвечает 401

#### Scenario: Черновик запрашивает уведомления
- **WHEN** пользователь с незаполненным профилем вызывает `GET /notifications`
- **THEN** система отвечает 200
