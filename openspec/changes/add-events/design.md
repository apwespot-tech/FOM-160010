# Design

## Context

Backend уже есть (`api/`): FastAPI с фабрикой приложения, синхронный SQLAlchemy 2 + psycopg 3, Alembic (миграция `0001`), ошибки `AppError` → `{"detail": {"code", "message"}}`, зависимости `CurrentUser` / `CompletedUser` / `AdminUser` в `app/deps.py`, часы приложения `app.state.clock` (в тестах — `FakeClock`). Тесты идут на реальной БД `app_test`, после каждого теста таблицы очищаются `TRUNCATE`. Требования — в `specs/events/spec.md`, мотивация — в proposal.md.

Роли `participant` и `organizer` сейчас есть у каждого пользователя, поэтому основное разграничение прав — «автор мероприятия или администратор», а проверка ролей нужна на будущее.

## Goals / Non-Goals

**Goals:**
- Лимит мест и правила «после начала» соблюдаются при любых одновременных запросах (запись, отказ, удаление участника, изменение лимита, удаление мероприятия).
- Каталог и карточка отдают вычисляемые поля одним запросом к БД на страницу, без N+1.
- Время во всех правилах берётся из часов приложения, чтобы тесты границ были детерминированными.

**Non-Goals:**
- Кеширование каталога, полнотекстовый поиск, курсорная пагинация.
- Фоновая очистка прошедших мероприятий.

## Decisions

### Схема БД (миграция `0002_events`)

```text
categories
  id          integer PK GENERATED BY DEFAULT AS IDENTITY
  name        varchar(50) NOT NULL UNIQUE

events
  id                uuid PK DEFAULT gen_random_uuid()
  organizer_id      uuid NOT NULL FK users(id) ON DELETE CASCADE
  category_id       integer NOT NULL FK categories(id) ON DELETE RESTRICT
  title             varchar(100) NOT NULL
  description       varchar(2000) NOT NULL
  place             varchar(200) NOT NULL
  starts_at         timestamptz NOT NULL
  duration_minutes  integer NULL      CHECK (duration_minutes BETWEEN 1 AND 1440)
  max_participants  smallint NOT NULL CHECK (max_participants BETWEEN 2 AND 100)
  min_age           smallint NOT NULL CHECK (min_age IN (0, 14, 16, 18))
  created_at, updated_at timestamptz NOT NULL DEFAULT now()
  INDEX ix_events_starts_at (starts_at, id)
  INDEX ix_events_category_starts_at (category_id, starts_at)

event_participants
  event_id    uuid FK events(id) ON DELETE CASCADE
  user_id     uuid FK users(id)  ON DELETE CASCADE
  joined_at   timestamptz NOT NULL
  PK (event_id, user_id)
  INDEX ix_event_participants_user_id (user_id)
```

- Миграция заполняет `categories` четырьмя значениями через `op.bulk_insert`; `downgrade` удаляет три таблицы.
- CHECK-ограничения дублируют валидацию Pydantic как последняя линия защиты; набор `min_age` — CHECK, а не enum Postgres: при изменении набора достаточно новой миграции с другим CHECK, без `ALTER TYPE`.
- Организатор хранится и в `events.organizer_id`, и строкой в `event_participants` (вариант A из обсуждения: он занимает место). Так `participants_count` — простой `count(*)`, а признак «организатор» — сравнение `user_id = organizer_id`.
- `joined_at` задаётся из часов приложения, а не `now()` БД: порядок списка участников и тесты не зависят от времени сервера БД.
- Категории — целочисленный `id`, а не UUID: справочник маленький и заполняется миграцией, удобно ссылаться в фильтрах.

Альтернатива — счётчик `participants_count` в `events`, изменяемый условным `UPDATE ... WHERE participants_count < max_participants`. Отклонена: дублирует данные, и для `PATCH` лимита всё равно нужна блокировка строки.

### Конкурентность: блокировка строки мероприятия

Все изменяющие операции (`PATCH`, `DELETE`, `join`, `leave`, `remove`) в одной транзакции:

```text
SELECT ... FROM events WHERE id = :id FOR UPDATE   -- нет строки -> 404
проверка прав                                     -- 403
проверка starts_at > now                          -- 409 event_started
проверки операции (возраст, already_joined, count(*) < max, ...)
INSERT / DELETE / UPDATE
COMMIT
```

Блокировка сериализует все операции над одним мероприятием, поэтому `count(*)` под ней точен, и уменьшение лимита не может разминуться с записью. Операции над разными мероприятиями не мешают друг другу. Это тот же подход, что и `pg_advisory_xact_lock` для телефона в `auth`, но блокируется сама строка.

- `INSERT` в `event_participants` ловит `IntegrityError` по PK как страховку и превращает в 409 `already_joined`.
- `leave` и `remove` удаляют строку `DELETE ... RETURNING`; пустой результат → `not_joined` / `participant_not_found`.

### Порядок проверок и коды ошибок

| Ручка | Порядок |
|-------|---------|
| `PATCH`, `DELETE` | 404 → 403 (не автор и не админ) → 409 `event_started` → 422 (дата, категория) → 409 `limit_below_participants` |
| `join` | 403 (нет роли `participant`) → 404 → 409 `event_started` → 409 `already_joined` → 403 `age_restricted` → 409 `event_full` |
| `leave` | 404 → 409 `event_started` → 409 `organizer_cannot_leave` → 409 `not_joined` |
| `remove` | 404 → 403 → 409 `event_started` → 409 `organizer_cannot_leave` → 404 `participant_not_found` |
| `GET .../participants` | не админ: нет записи пользователя → 403 (без поиска мероприятия); админ: 404 |

Проверка `already_joined` раньше возраста и лимита: записанному пользователю сообщаем, что он уже записан, а не что мест нет. Ошибки 422 с бизнес-кодом (`category_not_found`) и ошибки Pydantic имеют разные форматы `detail`, как и в `user-profile`; фронтенд уже умеет оба.

### Роли и права

- В `deps.py` добавляется фабрика зависимостей `require_role(role)` поверх `CompletedUser`: `OrganizerUser` для `POST /events`, `ParticipantUser` для `join`. Нет роли → 403 `forbidden`.
- Проверка «автор или администратор» — в сервисе (`_ensure_can_manage(event, user)`), потому что ей нужна загруженная строка мероприятия.
- Все ручки подключаются через `CompletedUser`, поэтому `profile_incomplete` и 401 работают так же, как в `profile`.

### Время и возраст

- «Мероприятие началось» — `event.starts_at <= now`, где `now` — `NowDep` (часы приложения). Создание и перенос требуют `starts_at > now`.
- Возраст — полных лет на `now.date()`; функция расчёта возраста, которой уже пользуется `ProfileOut`, выносится в общий модуль и переиспользуется.
- `starts_at` принимается как `AwareDatetime` Pydantic (без смещения → 422), хранится в `timestamptz`, отдаётся в UTC в ISO 8601.
- Фильтры `from` / `to` каталога — тоже `AwareDatetime`; условие `starts_at > now AND starts_at >= from AND starts_at < to`.

### Каталог и вычисляемые поля

Один `SELECT` на страницу:

```text
SELECT e.*, c.name, u.name AS organizer_name,
       (SELECT count(*) FROM event_participants p WHERE p.event_id = e.id) AS participants_count,
       EXISTS (SELECT 1 FROM event_participants p
               WHERE p.event_id = e.id AND p.user_id = :me) AS is_joined
FROM events e JOIN categories c ... JOIN users u ON u.id = e.organizer_id
WHERE <фильтры> ORDER BY e.starts_at, e.id LIMIT :limit OFFSET :offset
```

плюс `SELECT count(*)` с теми же фильтрами для `total`. Ответ — `{"items": [...], "total": N}`. `free_places` и `is_full` вычисляются в схеме ответа из `max_participants` и `participants_count`. Тот же запрос с `WHERE e.id = :id` используется для карточки и для ответа после изменений.

### Слои и файлы

```text
app/models/event.py          Category, Event, EventParticipant
app/schemas/event.py         EventCreate, EventUpdate, EventOut, EventPage, ParticipantOut, CategoryOut
app/services/event_service.py
app/routers/categories.py    GET /categories
app/routers/events.py        /events, join, leave, participants, remove
migrations/versions/0002_events.py
tests/test_categories.py, tests/test_events_crud.py, tests/test_events_catalog.py,
tests/test_events_participation.py
```

- `EventUpdate` запрещает лишние поля (`extra="forbid"`), поэтому `organizer_id` и `id` → 422; `null` допустим только для `duration_minutes`, для остальных полей → 422.
- В `tests/conftest.py` в `TRUNCATE` добавляются `events` и `event_participants`; `categories` не очищается — она заполнена миграцией. Хелперы: `create_event(...)`, `set_roles(...)` для проверки 403 без роли.
- Конкурентные тесты — потоки с `threading.Barrier`, как `test_concurrent_verify_of_same_code`.

## Risks / Trade-offs

- [Блокировка строки сериализует запись на одно популярное мероприятие] → при лимите до 100 мест и коротких транзакциях это незаметно; блокировка не затрагивает другие мероприятия.
- [`count(*)` в каталоге для каждой строки] → не больше 100 строк на страницу и индекс по PK `event_participants`; при росте можно перейти на денормализованный счётчик.
- [Удаление жёсткое: участники не узнают об отмене] → осознанно, статус отмены и уведомления — в бэклоге.
- [`organizer_id ON DELETE CASCADE`] → удаления пользователей в системе пока нет; при его появлении поведение пересмотреть.
- [`offset`-пагинация может пропускать или дублировать элементы при вставке между запросами] → допустимо для MVP.

## Migration Plan

1. Миграция `0002_events` создаёт таблицы и заполняет категории; применяется `alembic upgrade head` при старте контейнера `api`, как и `0001`.
2. Откат — `alembic downgrade 0001`: удаляет таблицы мероприятий; данные пользователей не затрагиваются.
3. Существующие ручки и данные не меняются, поэтому фронтенд из `add-web-auth` продолжает работать без изменений.
