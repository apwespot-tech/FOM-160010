# Design

## Context

- В сервисе нет хранения файлов: у пользователя только строка `photo_url`, в `api` нет обработки `multipart` (`python-multipart` не установлен), нет Pillow.
- `db` — единственное хранилище состояния (`docs/architecture.md`). Все изменения одного мероприятия сериализуются блокировкой строки `events` (`_lock_event`, `SELECT ... FOR UPDATE` в `event_service.py`).
- Авторизация только заголовком `Authorization: Bearer`, cookie нет (`docs/nfr.md`). Поэтому `<img src>` с адресом API не работает: браузер не передаст токен.
- Карточка и каталог собираются одним запросом `_view_query` (мероприятие + категория + организатор + подзапросы числа участников и признака записи).
- Создание и редактирование на frontend используют общий `EventFormFields.vue` и `useEventForm.ts`; окно создания — `CreateEventDialog.vue` + `useCreateEventDialog.ts`, просмотр и редактирование — `EventModal.vue`. HTTP-клиент `api/client.ts` (`apiFetch`) умеет только JSON, зато уже обновляет токен single-flight.

## Goals / Non-Goals

**Goals:**
- Фото хранятся транзакционно рядом с мероприятием, лимит 10 гарантирован и кодом, и БД.
- Байты фото никогда не читаются запросами карточки и каталога.
- Отдача фото требует access-токен и при этом не грузит одно и то же фото дважды.

**Non-Goals:**
- Уменьшенные копии, адаптивные размеры (`srcset`), ленивые превью в каталоге.
- Потоковая отдача (`Range`), ETag/304: фото неизменяемы, кеш бессрочный.
- Перенос в объектное хранилище — только оставить для него место в архитектуре.

## Decisions

### 1. Хранение в PostgreSQL, `bytea`, две таблицы

```
 events 1 --- * event_photos 1 --- 1 event_photo_data
                (метаданные)            (байты)
```

`event_photos`:
- `id uuid PK default gen_random_uuid()`;
- `event_id uuid FK events ON DELETE CASCADE`;
- `position smallint`, `CHECK (position BETWEEN 0 AND 9)`, `UNIQUE (event_id, position) DEFERRABLE INITIALLY DEFERRED` (порядок меняется в одной транзакции);
- `content_type varchar(20)`, `CHECK (content_type IN ('image/jpeg','image/png','image/webp'))`;
- `size_bytes integer`, `created_at timestamptz`.

`event_photo_data`: `photo_id uuid PK FK event_photos ON DELETE CASCADE`, `data bytea NOT NULL`.

Миграция `0003_event_photos.py` создаёт обе таблицы и индекс по `event_id` (покрыт `UNIQUE (event_id, position)`).

Почему так:
- `CHECK` на `position` 0–9 вместе с `UNIQUE` дублирует лимит в 10 фото в БД (требование `nfr.md`).
- Отдельная таблица для байтов гарантирует, что ни `select(Event)`, ни список фото не притащат мегабайты даже при неаккуратном запросе; отдельный `deferred`-столбец защищает хуже.
- Каскад удаляет фото с мероприятием без кода и без «висящих» файлов.

Альтернативы: Docker-том с файлами (нарушает «БД — единственное хранилище», нужна согласованность файл/строка и отдельный бэкап); MinIO/S3 (лишний сервис для MVP); base64 в `text` (+33 % места и декодирование на каждую отдачу).

### 2. Представление: `photos: [{id}]` в каждом ответе о мероприятии

В `_view_query` добавляется коррелированный подзапрос `array_agg(event_photos.id ORDER BY position)` (`coalesce` к пустому массиву). Это одна дешёвая выборка по индексу `(event_id, position)` и без JOIN к `event_photo_data`. Поле есть и в каталоге — когда появятся фото в карточках, API не придётся менять. Элемент — объект `{id}`, а не голый UUID: так в него позже можно добавить размеры или превью без поломки клиентов.

### 3. Отдача: `GET /events/{id}/photos/{photo_id}`

- Права — как у `GET /events/{id}`: `CompletedUser`. Запрос `event_photos JOIN event_photo_data WHERE id = photo_id AND event_id = id`; нет строки — 404 `photo_not_found` (не раскрываем, есть ли фото у другого мероприятия).
- Ответ `Response(content=data, media_type=content_type)` с заголовками `Cache-Control: private, max-age=31536000, immutable` и `X-Content-Type-Options: nosniff`.
- `id` фото неизменяем: замена фото = новая строка с новым `id`, поэтому инвалидация кеша не нужна.

### 4. Замена набора: `PUT /events/{id}/photos`, одна транзакция

Формат запроса (multipart):
- поле `order` — JSON-массив итогового порядка, элементы: `{"id": "<uuid>"}` для сохранённого фото или `{"file": <n>}` для n-го (с 0) файла в частях `files`;
- части `files` — новые файлы.

Порядок в сервисе:
1. Предварительная проверка без блокировки: мероприятие существует (404), `_ensure_can_manage` (403), `_ensure_not_started` (409). Посторонний пользователь получает 403 до того, как сервер начнёт читать и декодировать его файлы.
2. Разобрать и проверить `order`: корректный JSON, не больше 10 элементов (иначе `too_many_photos`), каждый файл использован ровно один раз, `id` без повторов (иначе `photo_list_invalid`).
3. Прочитать каждый файл не больше 2 097 153 байт (больше — `photo_too_large` с `extra: {"file": n}`), проверить и обработать через Pillow (решение 5). Тяжёлая работа идёт до блокировки строки, чтобы не держать `FOR UPDATE` на время декодирования.
4. `_lock_event`, затем повторно `_ensure_can_manage` и `_ensure_not_started`: за время обработки мероприятие могло начаться или быть удалено (тогда 404).
5. Проверить, что все `{"id"}` принадлежат мероприятию (`photo_list_invalid`).
6. Удалить фото, которых нет в списке; проставить `position` оставшимся и вставить новые. `UNIQUE` отложен до коммита, поэтому перестановки не конфликтуют.
7. Коммит, вернуть `EventOut`.

Любая ошибка на шагах 2–5 откатывает транзакцию целиком: набор фото не меняется, частично сохранённых файлов нет.

Почему одна ручка «заменить целиком», а не add/delete/reorder: так frontend отправляет итог формы одним запросом, «Отмена» в форме ничего не откатывает на сервере, а лимит и порядок проверяются атомарно под той же блокировкой, что и `PATCH`/`join` — одновременные запросы просто выстраиваются в очередь (сценарии «Одновременное изменение фото»).

Новые коды ошибок (`AppError`, 422): `too_many_photos`, `photo_too_large`, `photo_invalid`, `photo_list_invalid`; 404 `photo_not_found`. Для ошибок конкретного файла — `extra: {"file": n}`.

### 5. Проверка и обработка файлов — Pillow

- `Image.open` + `img.format in {"JPEG", "PNG", "WEBP"}`, иначе `photo_invalid`; `UnidentifiedImageError`/ошибки декодирования → `photo_invalid`.
- Защита от «бомб»: `Image.MAX_IMAGE_PIXELS = 40_000_000`, `DecompressionBombError`/`Warning` → `photo_invalid`.
- `ImageOps.exif_transpose(img)` — повернуть по ориентации, затем сохранить в исходном формате без `exif`/`icc`-метаданных: JPEG `quality=90, optimize=True`, WebP `quality=90`, PNG `optimize=True`. Пересохранение — единственный надёжный способ убрать EXIF у JPEG.
- Сохранённый файл может слегка отличаться по размеру от исходного; лимит 2 МБ относится к загружаемому файлу (спека), `size_bytes` хранит размер сохранённого.
- Вся обработка — в отдельном модуле `app/services/photo_processing.py`, чтобы тестировать её юнит-тестами без HTTP.

Альтернатива — проверка «магических байтов» без Pillow: не убирает EXIF и не ловит битые файлы.

### 6. Лимит размера запроса

Starlette складывает файлы в `SpooledTemporaryFile`, память не раздувается. Файл читается кусками с ранним отказом после 2 097 153 байт. Отдельный лимит на весь запрос не вводим: предел задают 10 файлов × 2 МБ. Dev-прокси Vite размер не ограничивает.

### 7. Frontend: загрузка с токеном и кеш по `id`

- `api/client.ts`: `apiFetch` получает поддержку `FormData` (без `Content-Type`, браузер ставит границу сам) и функцию `apiFetchBlob(path)` с той же логикой токена и повторной попытки после refresh.
- `composables/usePhotoUrl.ts`: модульный `Map<photoId, Promise<string>>` с `URL.createObjectURL(blob)`; одна загрузка на `id` даже при одновременных запросах; при ошибке запись удаляется, чтобы следующая попытка повторила запрос. `clearPhotoCache()` вызывает `URL.revokeObjectURL` для всех и вызывается при выходе (store `session`).
- Между перезагрузками страницы фото придёт из HTTP-кеша браузера благодаря `Cache-Control: private, immutable` (браузер кеширует ответы на запросы с `Authorization`, если ответ явно `private`). Это поведение не закрепляется спекой, только кеш в памяти.

Почему не подписанные ссылки — решение пользователя: строгое требование токена для каждого запроса файла.

### 8. Frontend: компоненты

- `EventGallery.vue` — просмотр: основное 16:9 (`object-fit: cover`), ряд миниатюр (горизонтальная прокрутка внутри блока), полноэкранный просмотр на PrimeVue `Galleria` в режиме `fullScreen` со своей разметкой счётчика. Показывается в `EventModal.vue` между шапкой и плитками, если `photos.length > 0`.
- `EventPhotosField.vue` — блок в форме: плитки (сохранённые — по `id` через `usePhotoUrl`, новые — `URL.createObjectURL(file)`), кнопки-иконки с `aria-label` и подсказками (удалить, сделать основным, влево, вправо), скрытый `<input type="file" multiple accept="image/jpeg,image/png,image/webp">`. На мобильном плитки в 3 колонки, кнопки не меньше 44 px (раздел «UI» в `rules.md`).
- Состояние формы: `useEventForm` получает поле `photos: PhotoDraft[]`, где `PhotoDraft = { kind: 'saved', id } | { kind: 'new', key, file, previewUrl }`, и признак «фото изменены» (сравнение со списком исходных `id`). Клиентская проверка — чистая функция `validatePhotoFiles(current, files)` в `utils/photos.ts` (тестируется отдельно); MIME проверяется по `file.type`, окончательно решает сервер.
- Сохранение в окне мероприятия: если изменены поля — `PATCH`; если изменены фото — `PUT` с `order` и новыми файлами; итоговый `EventItem` из последнего ответа обновляет окно и список. Ошибка `PUT` после успешного `PATCH` оставляет форму открытой с ошибкой у блока фото; исходные значения формы обновляются из ответа `PATCH`, чтобы повторное «Сохранить» не слало `PATCH` ещё раз.
- Создание: `useCreateEventDialog` запоминает `createdId` после `POST`. Если `PUT` фото упал — окно остаётся открытым, список обновляется, повтор «Создать» шлёт только `PUT`; закрытие окна в этом состоянии открывает `/events/<createdId>`.
- Превью новых файлов освобождаются (`revokeObjectURL`) при удалении плитки, сохранении и закрытии формы.

## Risks / Trade-offs

- [Рост БД и бэкапов: до 20 МБ на мероприятие] → для MVP приемлемо; отдельная таблица `event_photo_data` позволит перенести байты в S3, не трогая API и метаданные.
- [Каждая отдача фото — запрос к БД и копия байтов в память процесса] → кеш браузера бессрочный, повторных запросов почти нет; при росте нагрузки — S3/CDN.
- [Пересохранение JPEG теряет немного качества] → `quality=90` визуально без потерь; зато гарантированно нет геопозиции.
- [Запрос до ~20 МБ долго идёт по мобильной сети, пользователь не видит прогресса] → кнопка «Сохранить» в состоянии загрузки и блокировка формы; индикатор прогресса — позже (`fetch` его не даёт без `XMLHttpRequest`).
- [`PATCH` прошёл, `PUT` фото нет — частично сохранённое редактирование] → форма остаётся открытой с понятной ошибкой у блока фото, повтор отправляет только фото; поля уже сохранены, это видно по окну.
- [Декодирование больших картинок нагружает CPU] → лимит 2 МБ и `MAX_IMAGE_PIXELS`; обработка вне блокировки строки мероприятия.
- [Браузер может не кешировать ответы с `Authorization` между перезагрузками] → кеш в памяти покрывает основной сценарий; это не требование спеки.

## Migration Plan

1. Миграция `0003_event_photos` только добавляет таблицы — существующие данные не меняются, у всех мероприятий `photos = []`.
2. Пересборка образа `api` (новые зависимости `Pillow`, `python-multipart`): `docker compose up --build`.
3. Откат: `alembic downgrade 0002` удаляет обе таблицы вместе с фото; клиент без поля `photos` просто не показывает галерею.
