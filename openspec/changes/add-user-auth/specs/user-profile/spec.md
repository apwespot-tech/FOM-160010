# Spec Delta

## Purpose

Данные пользователя сервиса, их валидация и правила просмотра и изменения своего и чужого профиля, включая защиту контактных данных от посторонних.

## ADDED Requirements

### Requirement: Представление профиля
Профиль SHALL содержать: `id` (UUID), `phone` (E.164), `name`, `birth_date`, вычисляемый `age` (полных лет на текущую дату), `email`, `telegram`, `photo_url`, `roles` и `profile_completed`. Отсутствующие необязательные значения передаются как `null`.

#### Scenario: Возраст вычисляется по дате рождения
- **WHEN** у пользователя `birth_date` равна `2000-11-01`, а текущая дата `2026-10-31`
- **THEN** в профиле `age` равен 25

#### Scenario: День рождения сегодня
- **WHEN** у пользователя `birth_date` равна `2000-10-31`, а текущая дата `2026-10-31`
- **THEN** в профиле `age` равен 26

### Requirement: Заполненность профиля
Профиль SHALL считаться заполненным, когда у пользователя заданы `name` и `birth_date`. Признак `profile_completed` MUST вычисляться из этих полей.

#### Scenario: Новый пользователь
- **WHEN** пользователь только что создан при первом входе
- **THEN** `profile_completed` равен `false`, а `name` и `birth_date` равны `null`

#### Scenario: Заполнены оба поля
- **WHEN** пользователь задал `name` и `birth_date`
- **THEN** `profile_completed` равен `true`

### Requirement: Валидация полей профиля
Система SHALL отклонять с 422 некорректные значения: `name` — 1–100 символов после обрезки пробелов; `birth_date` — не позже текущей даты и не раньше `1900-01-01`; `email` — корректный адрес; `telegram` — `@` и 5–32 символа из латинских букв, цифр и `_`; `photo_url` — абсолютный URL со схемой http или https; `phone` — номер, приводимый к E.164.

#### Scenario: Дата рождения в будущем
- **WHEN** пользователь задаёт `birth_date` на день позже текущей даты
- **THEN** система отвечает 422 и профиль не меняется

#### Scenario: Дата рождения равна текущей
- **WHEN** пользователь задаёт `birth_date`, равную текущей дате
- **THEN** значение принимается

#### Scenario: Пустое имя
- **WHEN** пользователь задаёт `name` из одних пробелов
- **THEN** система отвечает 422

#### Scenario: Некорректный Telegram
- **WHEN** пользователь задаёт `telegram` равным `@abc`
- **THEN** система отвечает 422

### Requirement: Уникальность телефона и email
Телефон SHALL быть уникален среди всех пользователей; email, если задан, SHALL быть уникален без учёта регистра. Попытка задать занятое значение MUST отклоняться с 409; при одновременных попытках занять одно значение успешна MUST быть ровно одна.

#### Scenario: Занятый email
- **WHEN** пользователь задаёт email `Ann@Example.com`, а у другого пользователя уже есть `ann@example.com`
- **THEN** система отвечает 409

#### Scenario: Одновременное занятие email
- **WHEN** два пользователя одновременно задают один и тот же свободный email
- **THEN** одному запросу система отвечает 200, другому 409

### Requirement: Просмотр своего профиля
Система SHALL по `GET /profile` возвращать профиль текущего пользователя, в том числе при незаполненном профиле.

#### Scenario: Получение своего профиля
- **WHEN** авторизованный пользователь вызывает `GET /profile`
- **THEN** система отвечает 200 с его профилем, включая телефон

### Requirement: Изменение своего профиля
Система SHALL по `PATCH /profile` частично обновлять `name`, `birth_date`, `email`, `telegram` и `photo_url` текущего пользователя и возвращать обновлённый профиль. Необязательные поля можно очистить значением `null`; `name` и `birth_date` очистить нельзя (422). Передача `phone`, `roles` или `id` MUST отклоняться с 422.

#### Scenario: Заполнение профиля
- **WHEN** пользователь отправляет `PATCH /profile` с `name` и `birth_date`
- **THEN** система отвечает 200, и `profile_completed` равен `true`

#### Scenario: Очистка необязательного поля
- **WHEN** пользователь отправляет `PATCH /profile` с `telegram: null`
- **THEN** Telegram удаляется из профиля

#### Scenario: Попытка очистить имя
- **WHEN** пользователь отправляет `PATCH /profile` с `name: null`
- **THEN** система отвечает 422

#### Scenario: Попытка сменить свой телефон
- **WHEN** пользователь отправляет `PATCH /profile` с полем `phone`
- **THEN** система отвечает 422 и телефон не меняется

### Requirement: Просмотр чужого профиля
Система SHALL по `GET /profile/{id}` возвращать профиль, если запрашивает сам владелец или администратор. Администратору для несуществующего `id` система MUST отвечать 404. Остальным пользователям система MUST отвечать 403, в том числе для несуществующего `id`, не раскрывая, существует ли пользователь.

#### Scenario: Свой id
- **WHEN** пользователь запрашивает `GET /profile/{id}` со своим id
- **THEN** система отвечает 200 с его профилем

#### Scenario: Администратор смотрит чужой профиль
- **WHEN** администратор запрашивает профиль существующего пользователя
- **THEN** система отвечает 200 с полным профилем, включая телефон

#### Scenario: Администратор запрашивает несуществующий id
- **WHEN** администратор запрашивает профиль по id, которого нет
- **THEN** система отвечает 404

#### Scenario: Обычный пользователь смотрит чужой профиль
- **WHEN** пользователь без роли `admin` запрашивает профиль другого существующего пользователя
- **THEN** система отвечает 403

#### Scenario: Обычный пользователь запрашивает несуществующий id
- **WHEN** пользователь без роли `admin` запрашивает профиль по id, которого нет
- **THEN** система отвечает 403

### Requirement: Изменение чужого профиля администратором
Система SHALL по `PATCH /profile/{id}` позволять администратору частично обновлять `name`, `birth_date`, `email`, `telegram`, `photo_url` и `phone` любого пользователя с той же валидацией. Изменение `roles` и `id` MUST отклоняться с 422. Не-администратору система MUST отвечать 403; администратору для несуществующего `id` — 404.

#### Scenario: Администратор исправляет имя
- **WHEN** администратор отправляет `PATCH /profile/{id}` с новым `name`
- **THEN** система отвечает 200 с обновлённым профилем

#### Scenario: Не-администратор меняет чужой профиль
- **WHEN** пользователь без роли `admin` отправляет `PATCH /profile/{id}` для другого пользователя
- **THEN** система отвечает 403 и профиль не меняется

#### Scenario: Администратор задаёт занятый телефон
- **WHEN** администратор задаёт пользователю телефон, который уже принадлежит другому пользователю
- **THEN** система отвечает 409

### Requirement: Последствия смены телефона
При смене телефона пользователя администратором система SHALL отозвать все refresh-токены этого пользователя и отменить все неиспользованные коды входа для его прежнего номера. После этого вход MUST быть возможен только по новому номеру.

#### Scenario: Сессии сбрасываются
- **WHEN** администратор меняет пользователю телефон
- **THEN** все ранее выданные этому пользователю refresh-токены отклоняются с 401

#### Scenario: Вход по новому номеру
- **WHEN** после смены телефона пользователь запрашивает и проверяет код для нового номера
- **THEN** токены выдаются для того же пользователя, новый пользователь не создаётся
