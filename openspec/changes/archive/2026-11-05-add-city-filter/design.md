# Design

## Context

Мотивация и рамка — в `proposal.md`, требования — в `specs/events` и `specs/web-app`.

Что уже есть:
- `events.city_id` обязателен (`ON DELETE RESTRICT`), справочник `cities` около 40 строк. В `event_service` есть `_ensure_city_exists` с ошибкой 422 `city_not_found`.
- `GET /events` собирает условия списком в `event_service.list_events`. Новый фильтр — ещё одно условие, как `category_id`.
- Состояние списка на клиенте живёт в адресе: `useEventListQuery` (`parseListQuery`, `buildListQuery`, `toListParams`, `activeFilters`). Панель — `EventFilters.vue`: на компьютере поля в строке, на мобильном — в окне «Фильтры».
- Справочник городов на клиенте загружается один раз (`useCities`, по алфавиту). Город профиля — `session.profile.city`. В форме профиля уже есть `Select` с `filter` для городов.

## Goals / Non-Goals

**Goals:**
- Фильтр по городу ведёт себя так же, как остальные: адрес, «Сбросить», счётчик на мобильном, все вкладки.
- Порядок вариантов «Все города» → город профиля → остальные вычисляется на клиенте, без новых ручек.

**Non-Goals:**
- Изменения схемы БД и миграции. Индекс по `city_id` не добавляется (см. Risks).
- Общий компонент выбора города для профиля и фильтра: у них разные варианты и подписи.

## Decisions

### Backend: параметр и проверка города

`list_events` получает `city_id: int | None`. Если значение задано, сначала проверяется `_ensure_city_exists` (422 `city_not_found`), затем добавляется условие `Event.city_id == city_id`. Существующие проверки идут в прежнем порядке: проверка города — после проверки `scope`/`period` (`past_requires_scope`), перед построением запроса.

Альтернатива — пустой список для несуществующего города, как сейчас у `category_id`. Отклонена: в обсуждении выбрана явная ошибка, а клиент и так не отправляет `city_id`, которого нет в справочнике.

Схема БД не меняется, миграций нет.

### Frontend: состояние и адрес

- `EventListState.cityId: number | null`. `parseListQuery` принимает `city` — положительное целое, иначе `null`. `buildListQuery` пишет `city`, `toListParams` — `city_id` для всех вкладок. `activeFilters` учитывает город: он входит и в «Сбросить», и в «Фильтры (N)».
- Город в адресе, которого нет в справочнике (например, после удаления города администратором), клиент не проверяет: сервер ответит 422, и список покажет обычное состояние ошибки. Это редкий случай, его закрывает «Сбросить».

### Frontend: варианты поля

Вычисляемый список в `EventFilters.vue`:

```
[ {id: null, name: 'Все города'},
  {id: profileCity.id, name: profileCity.name, own: true},   // если город в профиле задан
  ...cities.filter(c => c.id !== profileCity?.id) ]          // уже по алфавиту
```

`Select` с `filter` и `filter-placeholder="Найти город"`, как в форме профиля; подпись «ваш город» — через слот `option`. Поиск PrimeVue по `option-label` без учёта регистра, этого достаточно. Поле стоит вторым после поиска. На мобильном оно в окне «Фильтры» первым.

Сетка панели: на ширине от 1024 px поиск занимает отдельную строку, под ним четыре поля (город, категория, даты, места). Пять полей в одну строку проверены на 1024 px: плейсхолдеры «Все категории» и «Свободных мест от» обрезались. На 640–1023 px — по-прежнему 2 колонки (поиск и город, категория и даты, места).

## Risks / Trade-offs

- [Фильтр по `city_id` без индекса] → Мероприятий немного, а условие объединяется с `ix_events_starts_at`. Индекс `(city_id, starts_at)` можно добавить отдельной миграцией, когда это понадобится; API от этого не меняется.
- [Панель фильтров на компьютере стала на строку выше] → Цена того, что поля не обрезаются; поиск во всю ширину удобнее для длинных запросов.
- [Город профиля меняется, пока открыт список] → Список вариантов вычисляется из сессии и обновится сам; выбранное значение в адресе не меняется.

## Migration Plan

Миграций нет. Backend и frontend выкатываются вместе; старый клиент новый параметр просто не передаёт.
