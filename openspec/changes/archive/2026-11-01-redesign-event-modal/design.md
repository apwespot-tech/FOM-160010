# Design

## Context

- Backend: `event_service._view_query` уже соединяет мероприятие с категорией и организатором (`User.name`), `list_participants` выбирает `User.id, User.name`. Поля `events.created_at`, `users.photo_url`, `users.telegram` есть в БД — миграции не нужны.
- Frontend: `/events/:id` — отдельная страница `EventView` (загрузка и действия) с `EventDetails` (просмотр/редактирование, `useEventForm` через `provide`) и `EventParticipants`. Список — `EventsView` с `useEventListQuery` (состояние в адресе) и `useEventList` (страницы, `watch` параметров).
- Мотивация и решения о данных — в proposal.md, требования — в `specs/events` и `specs/web-app`.

## Goals / Non-Goals

**Goals:**
- Окно поверх списка без перезагрузки списка ни при открытии, ни при закрытии.
- Telegram раскрывается только по правилу «записан или админ» — проверка на backend.
- Редактирование на месте без изменения размера окна.

**Non-Goals:**
- Анимации переходов между мероприятиями, листание соседних мероприятий из окна.
- Кеширование мероприятий между открытиями окна.

## Decisions

### Backend: поля и маскирование Telegram

- `_view_query` дополнительно выбирает `User.photo_url`, `User.telegram`; `EventView` получает `organizer_photo_url`, `organizer_telegram`; `created_at` берётся из строки мероприятия.
- Маскирование — в сервисе при сборке `EventView`: `organizer_telegram` остаётся, только если `is_joined` или пользователь — администратор, иначе `None`. Для этого `get_event_view` и `list_events` получают пользователя целиком (`list_events` уже получает). Одно место для правила — и для карточки, и для каталога.
- `OrganizerOut` и `ParticipantOut` получают `photo_url: str | None`, `telegram: str | None`; `EventOut` — `created_at`.
- Список участников и так доступен только записанным и админу, поэтому дополнительное маскирование там не нужно: запрос просто выбирает два новых столбца.

Альтернатива — отдельная ручка «контакты организатора». Отклонена: лишний запрос из окна, а правило доступа то же, что у признака `is_joined`, который уже вычисляется в том же запросе.

### Маршрут: окно — дочерний маршрут списка

```text
{ path: '/', component: EventsView, meta.complete,
  children: [{ path: 'events/:id', name: 'event', component: EventModal }] }
```

- `EventsView` остаётся смонтированным и рендерит `<RouterView />` для окна, поэтому список, прокрутка и подгруженные страницы не теряются.
- Карточки ссылаются на `/events/:id` **с текущим query списка** (`?tab=joined&category=3`): список под окном вычисляет своё состояние из того же `route.query`, а закрытие возвращает на `/` с тем же query.
- Закрытие (крестик, `Esc`, фон): если предыдущая запись истории — этот список (`history.state.back`), `router.back()`; иначе (прямая ссылка) `router.replace({ path: '/', query })`. «Назад» браузера работает само.
- `useEventList` следит за параметрами по их сериализации (`JSON.stringify(params)`), а не по ссылке на объект: при переходе в дочерний маршрут `computed` пересоздаёт объект параметров, и без этого список перезагружался бы.
- Прямая ссылка `/events/:id` без query открывает окно поверх «Найти компанию» — это поведение по умолчанию вкладок.

Альтернатива — окно без смены адреса (состояние в компоненте). Отклонена: теряются ссылки на мероприятие и «Назад», которые уже есть в спеке.

### Обновление списка под окном

`useEventList` получает `replaceItem(event)` и `removeItem(id)`; `EventsView` передаёт их окну через `provide('eventList', …)`. После записи, отказа, сохранения и исключения окно вызывает `replaceItem` с ответом сервера (карточка меняет места и отметки сразу), после удаления — `removeItem` и `total - 1`. Если изменённое мероприятие перестало подходить под фильтры (например, перенесено на другую дату), оно остаётся в списке до следующей загрузки — допустимо.

### Компоненты окна

```text
EventModal.vue          маршрутный компонент: Dialog, загрузка, действия, подтверждения
 |- EventSheet.vue      шапка (теги, название) + плитки + описание; просмотр/редактирование
 |    '- EventTile.vue  иконка, подпись, значение (или поле ввода), подстрочник
 |- OrganizerCard.vue   фото/инициалы, имя, «Организатор», «Создал …», «Написать»
 |- EventParticipants   (переработан) фото/инициалы, имя, Telegram-ссылка, «Исключить»
 '- footer              «Удалить»/«Редактировать» | «Отмена»/«Сохранить»; «Записаться»/«Отказаться»
PersonAvatar.vue        фото по photo_url, при ошибке загрузки или без фото — инициалы
```

- `EventView.vue`, `EventDetails.vue` удаляются; их логика переносится в `EventModal`/`EventSheet`. `useEventForm`, `EventFieldInput`, `eventFormContext` переиспользуются без изменений.
- Кнопки футера находятся в слоте `#footer` у `Dialog`, вне `<form>`: «Сохранить» связана с формой через атрибут `form="event-edit-form"` (как в окне создания).
- Плитки: сетка `1fr` на мобильном, `1fr 1fr` от 640 px, оформлены только для чтения — без подгонки под высоту полей ввода.
- Редактирование: по «Редактировать» тело окна заменяется формой `EventFormFields` — общим компонентом полей с подписями, который использует и окно создания (сетка в две колонки от 640 px). Шапка окна в редактировании — «Редактирование мероприятия» без тегов. Так режим просмотра не идёт на компромиссы ради полей, а форма не повторяет декоративную раскладку плиток (решение пользователя; стандарт в `docs/rules.md` обновлён).
- Иконки primeicons: `pi-calendar`, `pi-clock`, `pi-map-marker`, `pi-users`, `pi-crown` (тег «Вы организатор»), `pi-send` («Написать»). Тег «Вы организатор» — оранжевый акцент, категория — фиолетовый; без градиентов.
- Ширина окна: до 640 px на планшете и компьютере (окно с двумя колонками данных — по стандарту), во весь экран на мобильном. Содержимое прокручивается внутри, шапка окна и футер закреплены.
- Telegram-ссылка: `telegramUrl('@name') -> https://t.me/name`, `target="_blank"` и `rel="noopener noreferrer"`.
- «Создал мероприятие …»: `formatCreatedAt(iso, now)` в `utils/dates.ts` — «сегодня в HH:MM», «вчера в HH:MM», иначе «D месяца в HH:MM» (с годом, если не текущий).

## Risks / Trade-offs

- [Telegram становится виден другим участникам] → только участникам того же мероприятия и админу, правило записано в спеке; маскирование организатора — на backend и покрыто тестами.
- [`photo_url` — внешняя ссылка, картинка может не загрузиться или вести на чужой сервер] → `PersonAvatar` показывает инициалы при ошибке; `referrerpolicy="no-referrer"`. Загрузки фото по-прежнему нет.
- [Мероприятие в списке может устареть относительно фильтров после изменения] → обновляется при следующей смене фильтров или вкладки.
- [Окно поверх списка на мобильном занимает весь экран, фон не виден] → это требование стандарта; «Назад» возвращает к списку без перезагрузки.

## Migration Plan

Миграций нет. Новые поля API только добавляются, старые не меняются; фронтенд и backend выкатываются вместе.
