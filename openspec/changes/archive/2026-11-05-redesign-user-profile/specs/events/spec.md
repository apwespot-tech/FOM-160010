# Spec Delta

## MODIFIED Requirements

### Requirement: Представление мероприятия
Мероприятие SHALL содержать: `id` (UUID), `title`, `description`, `city` (`id`, `name`), `place`, `starts_at` (с часовым поясом), `duration_minutes` (или `null`), `created_at`, `category` (`id`, `name`), `max_participants`, `min_age`, `organizer` (`id`, `name`, `avatar_id`, `telegram`), `photos` (список `{id}` по порядку, первое — основное; пустой, если фото нет), вычисляемые `participants_count`, `free_places`, `is_full` и `is_joined`. `organizer.telegram` MUST заполняться только записанному на мероприятие пользователю и администратору, остальным — `null`.

#### Scenario: Новое мероприятие
- **WHEN** организатор создаёт мероприятие с `max_participants` = 5
- **THEN** в ответе `participants_count` = 1, `free_places` = 4, `is_full` = false, `is_joined` = true, `created_at` — момент создания, `photos` — пустой список, `city` — выбранный город, а `organizer` содержит `id` и имя автора

#### Scenario: Заполненное мероприятие
- **WHEN** на мероприятие с `max_participants` = 2 кроме организатора записался ещё один участник
- **THEN** в ответе `free_places` = 0 и `is_full` = true

#### Scenario: Ответ не раскрывает контакты организатора
- **WHEN** пользователь, не записанный на мероприятие и не администратор, получает мероприятие организатора с указанным Telegram
- **THEN** `organizer.telegram` = `null`, а телефона и email организатора в ответе нет

#### Scenario: Telegram организатора для участника
- **WHEN** записанный участник или администратор получает то же мероприятие
- **THEN** `organizer.telegram` содержит Telegram организатора, а телефона и email в ответе нет

#### Scenario: Фото организатора
- **WHEN** у организатора загружен аватар
- **THEN** `organizer.avatar_id` содержит его id для любого пользователя; без аватара — `null`; поля `photo_url` в ответе нет

#### Scenario: Фото мероприятия в ответе
- **WHEN** у мероприятия сохранены три фото и пользователь получает его через `GET /events/{id}` или в каталоге `GET /events`
- **THEN** `photos` содержит три элемента с `id` в сохранённом порядке, а содержимого файлов в ответе нет

### Requirement: Валидация полей мероприятия
Система SHALL отклонять с 422 некорректные значения: `title` — 1–100 символов после обрезки пробелов; `description` — 1–2000 символов после обрезки; `place` — 1–200 символов после обрезки; `starts_at` — дата и время с явным часовым поясом; `duration_minutes` — целое 1–1440 или `null`; `max_participants` — целое 2–100; `min_age` — одно из 0, 14, 16, 18; `category_id` — существующая категория; `city_id` — существующий город (обязателен при создании).

#### Scenario: Лимит на границах
- **WHEN** организатор создаёт мероприятие с `max_participants` = 2, а затем другое с `max_participants` = 100
- **THEN** оба мероприятия создаются

#### Scenario: Лимит за границами
- **WHEN** организатор создаёт мероприятие с `max_participants` = 1 или 101
- **THEN** система отвечает 422 и мероприятие не создаётся

#### Scenario: Недопустимое возрастное ограничение
- **WHEN** организатор создаёт мероприятие с `min_age` = 12
- **THEN** система отвечает 422

#### Scenario: Несуществующая категория
- **WHEN** организатор создаёт мероприятие с `category_id`, которого нет в справочнике
- **THEN** система отвечает 422 с кодом `category_not_found`

#### Scenario: Время без часового пояса
- **WHEN** организатор передаёт `starts_at` = `2026-12-01T19:00:00` без смещения
- **THEN** система отвечает 422

#### Scenario: Пустое название
- **WHEN** организатор передаёт `title` из одних пробелов
- **THEN** система отвечает 422

#### Scenario: Без города
- **WHEN** организатор создаёт мероприятие без `city_id`
- **THEN** система отвечает 422 и мероприятие не создаётся

#### Scenario: Несуществующий город
- **WHEN** организатор передаёт `city_id`, которого нет в справочнике
- **THEN** система отвечает 422 с кодом `city_not_found`

### Requirement: Изменение мероприятия
Система SHALL по `PATCH /events/{id}` частично обновлять `title`, `description`, `city_id`, `place`, `starts_at`, `duration_minutes`, `category_id`, `max_participants` и `min_age` и возвращать обновлённое мероприятие. Изменять MUST могут только автор и администратор, остальным — 403; несуществующий `id` — 404. Очистить значением `null` можно только `duration_minutes`. Новое `starts_at` MUST быть позже текущего момента. Передача `organizer_id` или `id` MUST отклоняться с 422.

#### Scenario: Автор меняет место
- **WHEN** автор предстоящего мероприятия отправляет `PATCH` с новым `place`
- **THEN** система отвечает 200, место изменено, остальные поля прежние

#### Scenario: Автор меняет город
- **WHEN** автор отправляет `PATCH` с `city_id` Казани
- **THEN** система отвечает 200, `city` — «Казань»

#### Scenario: Попытка очистить город
- **WHEN** автор отправляет `PATCH` с `city_id: null`
- **THEN** система отвечает 422 и город не меняется

#### Scenario: Администратор меняет чужое мероприятие
- **WHEN** администратор отправляет `PATCH` для мероприятия другого пользователя
- **THEN** система отвечает 200

#### Scenario: Посторонний пользователь
- **WHEN** пользователь, не являющийся автором или администратором, отправляет `PATCH`, в том числе будучи участником
- **THEN** система отвечает 403 и мероприятие не меняется

#### Scenario: Перенос в прошлое
- **WHEN** автор переносит `starts_at` на момент раньше текущего
- **THEN** система отвечает 422

#### Scenario: Попытка сменить организатора
- **WHEN** автор передаёт в `PATCH` поле `organizer_id`
- **THEN** система отвечает 422

### Requirement: Список участников
Система SHALL по `GET /events/{id}/participants` возвращать участников в порядке записи; каждый элемент содержит `id`, `name`, `avatar_id` и `telegram` (`null`, если не задано) и MUST NOT содержать телефон и email. Список MUST быть доступен записанным участникам (включая организатора) и администратору, в том числе после начала мероприятия, поэтому Telegram участников виден только им. Остальным — 403, в том числе для несуществующего `id`; администратору для несуществующего `id` — 404.

#### Scenario: Участник смотрит список
- **WHEN** записанный участник вызывает `GET /events/{id}/participants`
- **THEN** система отвечает 200, первым в списке идёт организатор, у каждого элемента есть `id`, `name`, `avatar_id` и `telegram`, но нет телефона и email

#### Scenario: Участник с Telegram
- **WHEN** у участника задан Telegram `@boris_k`, и другой записанный участник запрашивает список
- **THEN** элемент этого участника содержит `telegram` = `@boris_k`

#### Scenario: Участник без Telegram и фото
- **WHEN** у участника не заданы Telegram и аватар
- **THEN** его элемент содержит `telegram` = `null` и `avatar_id` = `null`

#### Scenario: Незаписанный пользователь
- **WHEN** пользователь, не записанный на мероприятие и не администратор, запрашивает список
- **THEN** система отвечает 403, контакты не раскрываются

#### Scenario: Несуществующее мероприятие для обычного пользователя
- **WHEN** пользователь, не являющийся администратором, запрашивает список участников несуществующего мероприятия
- **THEN** система отвечает 403, не раскрывая, существует ли мероприятие

#### Scenario: Несуществующее мероприятие для администратора
- **WHEN** администратор запрашивает список участников несуществующего мероприятия
- **THEN** система отвечает 404

#### Scenario: Бывший участник
- **WHEN** пользователь отказался от участия и запрашивает список
- **THEN** система отвечает 403

## ADDED Requirements

### Requirement: Город мероприятия
Каждое мероприятие SHALL относиться к городу из справочника `cities`; поле обязательно и хранится ограничением БД. Мероприятиям, созданным до появления городов, миграция MUST проставить город «Москва».

#### Scenario: Существующие мероприятия
- **WHEN** миграция применяется к БД с мероприятиями без города
- **THEN** у всех этих мероприятий `city` = «Москва»

#### Scenario: Мероприятие без города в БД
- **WHEN** в БД пытаются сохранить мероприятие без города
- **THEN** БД отклоняет запись
